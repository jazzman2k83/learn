Each course is developed in its own repo, which also holds private notes, learning records and statistics. Only the course's site files are copied here, into a topic folder such as `autosar/com/`. ## Add a course

From any course folder that has an `index.html` and is a git repo with at least one commit:

```sh
~/myAI/Teach/_LearningsOverview/tools/setup-course.sh .
```

Or ask Claude to "publish this course" (skill `publish-course`). The setup does the following:

1. It writes `course.json` and commits it in the course repo:
   ```json
   {
     "title": "AUTOSAR COM in plain words",
     "description": "One or two sentences for the landing page.",
     "path": "autosar/com",
     "language": "en",
     "topic": "AUTOSAR",
     "publish": ["index.html", "lessons", "reference", "assets", "config"]
   }
   ```
   `path` is the folder here (lowercase, `/`-separated). `topic` is the heading the course is grouped under on the landing page. `publish` is optional; the default is the list shown, using only the entries that exist.

   It also starts `CHANGES.md` with a "first version" entry (see [What's new](#whats-new)).
2. If the course repo has a GitHub remote, it installs `.github/workflows/publish-learn.yml` and sets the secret `HUB_DEPLOY_KEY`. From then on every push publishes the course.
3. It publishes the course once.

## Publish again

```sh
tools/publish.sh <course-dir>          # commit + push the hub
tools/publish.sh <course-dir> --no-push
tools/publish.sh <course-dir> --no-changes-entry   # see "What's new"
tools/unpublish.sh autosar/com         # remove a course
```

What gets published is the course's **committed** state (`git archive HEAD`). Uncommitted edits are never published, and the script warns when it finds them. Courses without a remote publish only this way. Courses with a remote can also publish this way, and their action does the same thing.

## Personal courses

Add `"audience": "personal"` to a course's `course.json` (and commit it in the course repo) to keep it off the landing page, "Recent updates" and `updates.html`. Such courses are listed only on `personal.html`, which nothing links to. Their pages, and `personal.html`, ask search engines not to index them (`<meta name="robots" content="noindex">`), and their "All courses" link leads to `personal.html`.

This only makes them less visible: this repo is public, so anyone can still find the files here. Without the field, a course is listed normally.

## What's new

Every course keeps `CHANGES.md` at its root: its change history for learners, written by hand (or drafted by Claude from `git log` and checked). Newest entry first:

```markdown
# Changes

## 2026-11-08
- New: [Lesson 18 – The whole call sequence](lessons/0018-the-whole-call-sequence.html)
- Changed: Lesson 14 now points ahead to lesson 18.
- Fixed: Wrong bit position in the example of lesson 16.
```

Each entry is `## YYYY-MM-DD` with `- ` items. An item may start with a kind: New, Changed, Fixed, Removed (German: Neu, Geändert, Korrigiert, Entfernt). `[text](link)` links are relative to the course folder, and `` `code` `` is allowed. Anything else stops the publish with the line number.

`tools/publish.sh` copies `CHANGES.md` along with the course, whatever the `publish` list says, and `tools/changes.py` turns it into:

- `<path>/changes.html`, the course's "What's new" page ("Neuigkeiten" in German courses), linked from the common bar on every page of the course;
- on the landing page, "Updated <date>" on the course's card, with a "New" mark for 14 days (set in the browser by `assets/hub.js`), and "Recent updates", the 3 newest entries of all courses in one line each, linking to `updates.html` with all of them.

**It can't be forgotten.** `<path>/publish-state.json` records a hash of the published files and of `CHANGES.md` at each publish. If the published files changed since then but `CHANGES.md` didn't, `publish.sh` stops, and so does the course's action, which shows up as a failed run. For a change learners need not hear about, use `--no-changes-entry`, or put `[skip changes]` in the course's last commit message (that works for the action too). `course.json` and `CHANGES.md` themselves don't count as changed content. The rule for agents is in `~/myAI/Teach/AGENTS.md`.

## Common bar and theme

Courses keep their own look, but the published copy gets the hub's frame: `tools/publish.sh` runs `tools/harmonize.py` on every course after copying it, so a new version pushed from a course repo gets it too, and the course repo itself never changes. It

- puts a bar on top of every page: "All courses", the course title, "What's new" (if the course has `CHANGES.md`), and one light/dark toggle (`assets/hub-course.css`). The choice holds for the whole hub (`assets/hub.js`, key `learn-hub-theme`), and a course's own toggle is hidden;
- makes each `@media (prefers-color-scheme: dark)` block in the course's CSS follow that toggle, so courses that only follow the system setting can be switched too.
- adds a one-line notice at the end of every page (unofficial, written with AI, not fully reviewed), in the course's language, linking to `about.html`.

A course looks right with it if its dark colours sit in `@media (prefers-color-scheme: dark)` blocks (or already use `data-theme="dark"` on `<html>`). Scripts that ask `matchMedia('(prefers-color-scheme: dark)')` get the chosen theme.

## Deploy key

The actions push here with one deploy key that has write access on this repo. Its private half is stored outside every repo, at `~/.config/learn-hub/hub_deploy_key`, and `setup-course.sh` copies it into each course repo's `HUB_DEPLOY_KEY` secret. If the key is lost, generate a new one, add it as a deploy key here, then run `gh secret set HUB_DEPLOY_KEY -R <repo> < key` for each course repo.
