Large I-PDUs and dynamic length signals

So far an I-PDU was a few bytes of fixed size. Three special cases remain: an I-PDU too big for one frame of the bus, a signal whose length changes, and data that COM should pass through without unpacking it.

1. Large I-PDUs

What the bus carries in one go is a frame (in AUTOSAR an L-PDU: the unit of the data link layer). A classic CAN frame holds 8 bytes of data, a CAN FD frame up to 64. An I-PDU that is bigger cannot travel in one frame.

Such an I-PDU is a large I-PDU (an I-PDU that does not fit into one frame of the bus). COM does not cut it up itself. Its configuration says that the I-PDU goes via a transport protocol (a module below the PduR, for example CanTp, that splits a large I-PDU into several frames and joins them again on the other side).

Try it

For COM, a large I-PDU behaves a little differently:

  • Transmission takes time. While the frames are going out, COM leaves the content of the I-PDU alone. If the same I-PDU is triggered again before the transmission is finished, COM skips that extra transmission and reports an error.
  • Reception can fail halfway. If the frames do not all arrive, COM treats every signal in that I-PDU as if it had received the data invalid value (lesson 7).

2. Dynamic length signals

A text or a list may be 3 bytes long one time and 20 the next. COM supports one kind of signal for this: the dynamic length signal (a signal of type UINT8_DYN: a byte array whose length can change from one transmission to the next). Its maximum length is fixed in the configuration. The RTE writes and reads it with Com_SendDynSignal and Com_ReceiveDynSignal (COM APIs that pass the value together with its current length).

It must be last

The dynamic length signal sits at the very end of its I-PDU, behind all signals of fixed size.

The length is not sent

The I-PDU simply gets shorter or longer. The receiver works out the length of the signal from the length of the I-PDU it received.

3. The Large Data Path

Sometimes the data is already a finished block of bytes, made by the RTE or another part of the software. This is common for service data on Ethernet. COM has nothing to pack, convert or filter. For such an I-PDU COM offers the Large Data Path (a way through COM without packing, conversion, filtering and without a copy in COM). The I-PDU then holds exactly one signal, a byte array, and COM passes it straight through in both directions.

There is no periodic timer and no TRIGGERED here: the RTE requests each transmission itself with Com_Transmit (COM API: send this I-PDU now), or a lower layer asks for the content with Com_TriggerTransmit (a COM callback: give me the content of this I-PDU now; more in lesson 14). Up to release R24-11, so also in 4.4.0 and R20-11, this was a separate module next to COM: LdCom (Large Data COM), which the RTE calls with LdCom_Transmit. R25-11 merged it into COM as the Large Data Path; Com_Transmit exists only from then on. Sections 1 and 2, large I-PDUs and dynamic length signals, were part of COM in those older releases already.
