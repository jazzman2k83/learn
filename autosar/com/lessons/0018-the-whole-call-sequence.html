AUTOSAR COM

The whole call sequence

Lesson 14 showed the layers between the SWC and the bus. This lesson follows one signal through them call by call, with the real function names, on transmission and on reception. It also shows where each call runs: in a task of the SWC, in an interrupt, or in a main function.

How to read the diagram

One column per module

Each module has a column with a dashed line below it, its lifeline. Time runs downwards. COM is the green column.

Calls and returns

A solid arrow is a function call, from the caller to the module that provides the function. A dashed arrow is the return value coming back. A grey box is work inside one module.

Contexts

A grey band marks where a new piece of code starts running: a runnable (a function of an SWC that the RTE starts in an OS task), an interrupt of the hardware, or a main function called by the scheduler. Everything below a band runs inside it, until the next band.

The example is one signal, the vehicle speed, sent by one ECU and received by another. The SWC writes it with Rte_Write (the RTE API for writing a data element of a port) and the receiving SWC reads it with Rte_Read (the RTE API for reading one). The port is called VehicleSpeed and the data element Speed, so the real names are Rte_Write_VehicleSpeed_Speed and Rte_Read_VehicleSpeed_Speed.

Things to notice

  • COM has only two neighbours here. It calls nobody but the PduR and the RTE, and nobody else calls it. CanIf, SoAd and the drivers are always reached through the PduR.
  • No call waits for the bus. Com_SendSignal returns before anything is sent, and PduR_ComTransmit returns before the frame is on the bus. The result comes back later as a separate call from below: Com_TxConfirmation.
  • The context changes two or three times. A transmission starts in a runnable, goes out in a main function of COM (or still inside Com_SendSignal), and is confirmed in an interrupt or a main function of a lower module. Reception starts in an interrupt and ends in a runnable.
  • signal processing decides where COM's work runs. With IMMEDIATE the reception steps and the notification run inside Com_RxIndication, often in an interrupt. With DEFERRED COM only copies the I-PDU there and does the rest in Com_MainFunctionRx.
  • A transmit confirmation does not mean the same on every bus. On CAN it means the frame was sent on the bus. On Ethernet with UDP, SoAd confirms in its next SoAd_MainFunction once TcpIp_UdpTransmit has accepted the data. That shows the I-PDU was handed on, not that it reached the network.
  • With CanTp, COM sees no frames. CanTp asks COM for the bytes piece by piece (Com_CopyTxData) and gets the frame confirmations itself. COM only hears at the very end, with Com_TpTxConfirmation.

The same chain in other set-ups

The diagram shows the common case. Real ECUs often have more modules in the chain, or fewer. COM's own calls stay the same in all of them.

IpduM between PduR and CanIf

With IpduM (I-PDU Multiplexer: puts several I-PDUs into one container I-PDU), the PduR sends COM's I-PDU to IpduM first. IpduM collects it and later hands the container I-PDU on through the PduR. The confirmation comes back the same way.

SecOC between PduR and CanIf

With SecOC (Secure Onboard Communication: adds an authenticator to an I-PDU), the PduR routes COM's I-PDU to SecOC. SecOC adds the authenticator and transmits the secured I-PDU through the PduR. On reception COM only gets the I-PDU after SecOC has checked it.

Com_TriggerTransmit

Some I-PDUs are fetched instead of pushed. Just before the frame goes out, the lower layer calls Com_TriggerTransmit through the PduR and COM copies the current content. This is the rule on LIN and FlexRay, and an option on CAN (CanIf can ask at the time of Can_Write).

The hardware is busy

If the CAN Driver has no free transmit buffer, Can_Write returns CAN_BUSY. CanIf can then keep the L-PDU in its own transmit buffer and send it after the next CanIf_TxConfirmation. COM does not notice: for COM the call was successful.

TCP instead of UDP

On a TCP socket connection SoAd confirms only when TCP has acknowledged all the data, inside the confirmation callback of TcpIp. The confirmation then means that the TCP stack of the other side has acknowledged the data.

Serialized data on Ethernet

Service-oriented data is often serialized above COM by a transformer and then passed through COM on the Large Data Path (Com_Transmit, lesson 13). Or the RTE uses LdCom (Large Data COM: a slim alternative to COM for such data) and COM is not in the chain at all.

Gateways

The PduR can route an I-PDU from one bus straight to another without COM. The signal gateway of COM (lesson 12) copies single signals instead: reception ends in COM, and Com_MainFunctionRouteSignals starts a new transmission.

Interrupt or polling

Every driver can work in interrupt mode or in polling mode (it checks the hardware in its own main function, for example Can_MainFunction_Read). The call chain above it stays the same; only the context in the band changes.
