Synchronized PNC shutdown

In a hierarchy of PNC gateways, the release of a PNC creeps from level to level, one reset time at a time, and the ECUs leave the PNC at different moments. A synchronized shutdown lets the top of the hierarchy announce the end to everyone at once.

Lesson 44 built the hierarchy of top-level coordinator, intermediate coordinators and leaf nodes. This lesson shows the problem a release runs into there, and the message and calls that R25-11 adds to solve it.

A release takes one reset time per level

Take Comfort in the hierarchy of lesson 44: a top-level PNC coordinator on Ethernet, the body gateway as intermediate PNC coordinator (Eth passive, BodyCan active), and the Door ECU as PNC leaf node. (In the example ECU itself both channels are active and the gateway is the top-level coordinator; the coordinator above is added here to show all three roles.) The Door ECU releases Comfort, and nobody else requests it. Nothing announces the release; every coordinator only notices that a bit is no longer repeated:

  1. The gateway's ERA bit for body CAN falls to 0 after one PNC reset timer period. The gateway stops reporting Comfort upwards, but it keeps sending Comfort on body CAN: the top-level coordinator still mirrors it on Ethernet.
  2. One reset time later, the top-level coordinator's ERA bit falls. It releases Comfort and stops sending it.
  3. One more reset time later, the gateway's ERA bit for Ethernet falls. Only now does the gateway release Comfort and stop sending it on body CAN.

So the top-level coordinator's EIRA bit runs out a full reset time before those of the gateway and the Door ECU. The PNC goes to COMM_PNC_PREPARE_SLEEP at different moments on different ECUs, and an application on one ECU may stop sending while its partners still expect its signals: they see timeouts.

The PN shutdown message

With synchronized PNC shutdown (the top-level coordinator announces the release of a PNC in one message that every coordinator passes on at once, so that all ECUs restart their reset timers together) the top-level coordinator does not just go quiet. When it releases a PNC, it sends a PN shutdown message (an NM PDU with the PN Shutdown Request Bit set and a 1 for every PNC that is shut down). Each NM PDU with this bit makes every receiver restart the reset timer of those PNCs, and every intermediate coordinator passes it down at once. So all reset timers of the PNC restart at almost the same moment, and all ECUs reach COMM_PNC_PREPARE_SLEEP together.

The flag is the PN Shutdown Request Bit (PNSR: bit 1 of the Control Bit Vector, set to 1 in a PN shutdown message). An ECU that is not a coordinator needs no change: it handles the PN shutdown message as an ordinary NM PDU, which simply requests the PNC once more.

The calls, top to bottom

ComM decides, NmIf keeps the bookkeeping, and the bus NMs send and receive the message. Step through the release of Comfort, first on the top-level coordinator, then on the body gateway as intermediate coordinator:

Some details complete the picture:

  • Only a top-level coordinator starts a shutdown: ComM calls Nm_RequestSynchronizedPncShutdown (ComM asks NmIf to announce the shutdown of one PNC on one channel) when the PNC leaves COMM_PNC_REQUESTED and all channels of the PNC are active.
  • NmIf stores the request per channel and handles it in its main function: it calls CanNm_ActivateTxPnShutdownMsg or UdpNm_ActivateTxPnShutdownMsg (NmIf tells the bus NM to send PN shutdown messages), and the deactivate counterpart when no request is left. The bus NM sends the message in its next main function, before any cyclic NM PDU.
  • When the bus NM confirms the transmission, NmIf removes the PNCs from its list. Optionally a retransmission time limits how long it keeps trying; if the message still cannot be sent, NmIf drops the request and reports a runtime error to Det. The PNC then shuts down without synchronization.
  • A new request wins. If the PNC is requested again, locally or by a received NM PDU, before the message is out, NmIf removes it from its list. An intermediate coordinator does not forward a shutdown while a local user or an active channel still requests the PNC; it can request the network again instead.
  • A PN shutdown message received on an active channel is a design error: CanNm reports it as a runtime error and treats the NM PDU as an ordinary one.
  • In the example ECU as configured, with BodyCan and Eth both active, the body gateway is the top-level coordinator: it sends the PN shutdown message itself, on body CAN and on Ethernet.
  • For PNCs handled in one direction only, or mapped to a channel for transmission only (lesson 44), no synchronized shutdown takes place.

4.4.0 has no synchronized PNC shutdown. R20-11 describes it as a draft with other interfaces: Nm_ForwardSynchronizedPncShutdown had no parameters, ComM_Nm_ForwardSynchronizedPncShutdown only a channel, and NmIf passed each request on to CanNm_RequestSynchronizedPncShutdown or UdpNm_RequestSynchronizedPncShutdown, so the bus NM kept the pending PNCs. R21-11 and R22-11 changed this into the R25-11 form: NmIf keeps the pending PNCs and switches the message on and off with CanNm_ActivateTxPnShutdownMsg and CanNm_DeactivateTxPnShutdownMsg, which are valid since R22-11.

Things to notice. Without synchronization the release of a PNC costs one reset time per level, and the levels finish at different times. The PN shutdown message is an NM PDU that requests the PNC one last time, with the PN Shutdown Request Bit set: everyone restarts the same timer at nearly the same moment. Only the top-level coordinator starts it, intermediate coordinators forward it at once, leaf nodes need nothing new.
