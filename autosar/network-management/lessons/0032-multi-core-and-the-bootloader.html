Multi-core and the bootloader

On a microcontroller with several cores, EcuM runs once on every core, and one of them leads. A short look at how the cores start, stop and sleep together, and at how software asks for the bootloader at the next reset.

This lesson is an overview. The phases are the same as on a single core; what changes is who does what, and how the cores wait for each other.

One EcuM per core

The BSW is distributed over partitions (independent sections of the software, each mapped to exactly one core). EcuM exists once per core, BswM once per partition. The master core (the core whose EcuM the bootloader starts first, through EcuM_Init) leads; every other core is a slave core (a core that the master core starts, with its own satellite EcuM). Which core is the master is decided by the bootloader. If the same EcuM code runs on every core, it first tests on which kind of core it is and acts accordingly.

Startup, shutdown and sleep

PhaseMaster coreSlave cores
STARTUPInitializes the first drivers, determines the post-build configuration, does the reset and wakeup housekeeping, then activates all slave cores.Each runs its startup code, which calls EcuM_Init on that core. Every EcuM starts its OS and SchM and initializes its core's BswMs; the OS synchronizes the cores.
UPThe main function of EcuM runs on every core, and each EcuM handles the wakeup events of its own core. The BswMs decide, as on a single core.
SHUTDOWNBswM in the master's partition calls EcuM_GoDownHaltPoll. The master EcuM starts the slave shutdown, waits until every slave has signalled readiness, then calls ShutdownAllCores.Each EcuM de-initializes its BswM and SchM, checks for wakeup events, and signals that its core is ready.
SLEEPWaits until all slave cores are halted before it computes the RAM checksum, and checks it before it releases them again.Prepare through their own BswM and halt; EcuM takes its own resource on each core.

A single core cannot shut down while the others go on: the shutdown targets OFF and RESET stop all cores together, and SLEEP puts all cores to sleep. The synchronization uses OS events across cores, as in the example the specification gives: each slave sets an event, and the master waits until it has seen all of them.

Boot targets

The bootloader is not part of AUTOSAR, but the application must be able to ask for it, for example when a diagnostic tester wants to reprogram the ECU. The bootloader, the system supplier bootloader and the application are separate program images, and the only way from one to another is a reset. A boot menu after the reset branches into the image that the boot target (where the ECU goes after the next reset) names:

ECUM_BOOT_TARGET_APP

Application

The ECU boots into the application.

ECUM_BOOT_TARGET_OEM_BOOTLOADER

OEM bootloader

The ECU boots into the bootloader of the vehicle manufacturer.

ECUM_BOOT_TARGET_SYS_BOOTLOADER

System supplier bootloader

The ECU boots into the bootloader of the ECU supplier.

EcuM_SelectBootTarget stores the target where the boot menu finds it after the reset, in a format and location that fit the bootloader in use. EcuM_GetBootTarget reads it back. The service is meant only for SWCs related to diagnostics. Selecting a boot target does not reset the ECU; that still takes a shutdown with the target RESET.

Things to notice. On a multi-core ECU the phases stay the same; the master EcuM starts the slaves first and stops them last, and nothing shuts down alone. A boot target takes effect only at the next reset.
