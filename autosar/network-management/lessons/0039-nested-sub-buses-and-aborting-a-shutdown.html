Network and Mode Management in AUTOSAR Classic

Network Management

Nested sub-buses and aborting a shutdown

Gateways can be chained: a gateway below another one must wait for the signal from above before it starts its coordinated shutdown. And a shutdown that has started can still be called off when somebody needs a bus again.

A different configuration of the gateway. As in lessons 37 and 38, the gateways here use the NM coordinator without partial networking in NmIf (a project without PNCs, or an older release). In R25-11 an NmIf supports either the NM coordinator or partial networking, not both.

Lessons 37 and 38 showed one NM coordinator on its own. This lesson adds coordinators in a chain, the three levels of synchronization the specification describes, and what happens when a shutdown is aborted or a bus wakes up.

A chain of coordinators

A bus that is reached through a second gateway is a nested sub-bus (a bus behind a gateway that is itself on a bus coordinated by another gateway). Its gateway runs a coordinator too. If both coordinators decided on their own, they could keep the shared bus awake for each other: each still sends NM PDUs, so each sees the other as "not ready to sleep". The specification solves this with a hierarchy, set up per channel of each coordinator:

  • An actively coordinated channel (a channel on which this coordinator leads: it keeps the bus awake and shuts it down with its own timers) is one on which the coordinator behaves as in lessons 37 and 38.
  • A passively coordinated channel (a channel on which a coordinator higher up leads, and this coordinator follows) is the one towards the higher coordinator. There, the lower coordinator sends NM PDUs only while it has a network request of its own or while one of its actively coordinated buses is not ready to sleep. So when it is ready, it falls silent, and the higher coordinator can see that.

The top coordinator of a cluster has only actively coordinated channels. The chain needs coordinator synchronization support to be configured in NmIf and in the bus NMs.

The Sleep Ready bit travels down

A lower coordinator does not start its shutdown by itself. It waits for the NM Coordinator Sleep Ready Bit (a bit in the NM PDU: set to 1, it tells the coordinators below to start their coordinated shutdown; set back to 0, it calls the shutdown off) on its passively coordinated channel:

  1. The top coordinator finds all its buses ready to sleep and starts its coordinated shutdown. On its actively coordinated channels it sets the Sleep Ready bit to 1; the bus NM sends one NM PDU with the bit at once.
  2. The bus NM of the next gateway receives the bit on its passively coordinated channel and reports it to NmIf. That coordinator sets the bit on its own actively coordinated channels and starts its coordinated shutdown.
  3. So the bit travels down the chain, one gateway at a time. If the top coordinator clears the bit again, each gateway clears it on its active channels too.

Because the lower gateways start a little later, the global coordinator time of the top coordinator must cover the whole chain, nested buses included.

Three levels of synchronization

How closely the buses are synchronized depends on the configuration. The specification describes three use cases; they differ in two settings: whether one bus is the synchronizing network (a bus whose NM tells the coordinator suitable moments to start the shutdown, typically a cyclic bus such as FlexRay), and how long the global coordinator time is.

Use caseSynchronizing networkGlobal coordinator timeResult
1. Synchronous commandnone0All buses are released at the same moment; they reach bus sleep one after the other. The fastest total shutdown.
2. Synchronous initiationone0Like 1, but the release waits for a suitable moment on the synchronizing network.
3. Synchronous network sleeponethe longest shutdown time, rounded up in cycles of the synchronizing networkThe buses are released with delays and reach bus sleep together.

The example gateway has only CAN and Ethernet. CanNm gives no synchronization points, because a CAN bus can be released at any moment, and the gateway has no synchronizing network. Without one, the coordinator starts its timers as soon as the shutdown conditions are met. With a global coordinator time as in lesson 38, the gateway gets the result of use case 3: all buses sleep together.

Aborting a coordinated shutdown

Between the start of the shutdown and the last bus falling asleep, a few seconds pass. If somebody needs a bus again during that time, the coordinator aborts the shutdown. Four events do that, on any bus of the cluster:

  1. An ECU on a bus that is not released yet starts requesting it again: the bus NM reports a remote sleep cancellation.
  2. An ECU on a bus that was released and is in Prepare Bus-Sleep Mode sends an NM PDU: the bus NM goes back to Network Mode and reports it.
  3. ComM requests one of the buses, with Nm_NetworkRequest or Nm_PassiveStartUp.
  4. On a passively coordinated channel, the coordinator above clears the Sleep Ready bit.

Then the coordinator requests the network again on every bus that has not reported Bus-Sleep Mode, released or not, and clears the Sleep Ready bit on its active channels. It does not wake a bus that already sleeps: for those it sends ComM a restart indication, and ComM decides, as in any wakeup. After that the coordinator checks the shutdown conditions again, and a new coordinated shutdown starts as soon as they are met. If a bus NM refuses a release, the coordinator also aborts and requests all awake buses again.

Wakeup and the coordinator

NmIf does not wake buses; ComM does. When another ECU wakes a coordinated bus, the bus NM reports the network start to NmIf, NmIf passes it to ComM, and ComM calls Nm_PassiveStartUp. For a bus in a coordination cluster the coordinator treats that call like Nm_NetworkRequest: it requests the network on that bus, so the bus counts as requested by the coordinator. The network start report alone does not abort a coordinated shutdown; the following call from ComM does.

Whether the other buses of the cluster come up as well is a ComM configuration: ComM can start every bus of the cluster when one of them reports a network start. The specification recommends that for coordinated buses, but it is not required.

In 4.4.0 and R20-11 the chain of coordinators, the Sleep Ready bit, the three use cases and the abort rules are the same as in R25-11. The only change is the one noted in lesson 38: until R24-11 the shutdown timers are started for every awake channel of the cluster, since R25-11 for every awake, actively coordinated channel.

Things to notice. A lower gateway stays silent on the bus towards the gateway above as soon as it is ready, so that the gateway above can detect that all are ready; then it waits for the Sleep Ready bit. An abort never wakes a sleeping bus by itself; ComM decides that. The NM coordinator and ComM share the work: NmIf keeps awake and shuts down, ComM wakes up.
