Network Management

RUN and POST_RUN requests

An SWC that still has work to do must be able to say so before the ECU goes down. EcuM collects these requests and reports what they add up to, and BswM decides what happens next.

This lesson shows who may place such requests, the four calls for them, what EcuM tells BswM, and why a request alone does not keep the ECU running.

EcuM users

Only an EcuM user (a configured identifier for an SWC or another entity that uses the interfaces of EcuM; each one has its own number of type EcuM_UserType) may place requests. An SWC reaches EcuM through an RTE port of the service interface EcuM_StateRequest. The RTE adds the user number as a port-defined argument, so the SWC does not pass it itself and cannot speak for another user.

In the example ECU, BodyControl is an EcuM user. To show how several requests add up, this page adds a second SWC, called Logger here, which writes some data to memory before the ECU goes down.

Four calls

A RUN request (a request from an EcuM user that the ECU stays in its RUN mode) and a POST_RUN request (a request for time after the last RUN request is gone, to finish work such as saving data or switching off peripherals) are placed and released with four calls:

keep running

EcuM_RequestRUN

Places a RUN request for this user. EcuM_ReleaseRUN (releases it again) ends it.

time before going down

EcuM_RequestPOST_RUN

Places a POST_RUN request. EcuM_ReleasePOST_RUN (releases it again) ends it.

Requests do not nest: one user holds at most one RUN request and one POST_RUN request, tracked independently. A second request from the same user, or a release without a request, is a development error (ECUM_E_MULTIPLE_RUN_REQUESTS, ECUM_E_MISMATCHED_RUN_RELEASE). The order matters: a user that needs time in POST_RUN must request POST_RUN before it releases RUN. Otherwise nothing guarantees that it still gets to run its POST_RUN code.

What EcuM reports to BswM

With ECU Mode Handling (the optional cooperation of EcuM and BswM about the modes RUN and POST_RUN) configured, EcuM checks the requests of all users in its main function and reports the result with BswM_EcuM_RequestedState (EcuM tells BswM which state its users request and whether that is requested or released). BswM receives it as a mode request.

WhenEcuM calls
The first RUN or POST_RUN request arrivesBswM_EcuM_RequestedState(ECUM_STATE_RUN, ECUM_RUNSTATUS_REQUESTED)
The last RUN request is releasedBswM_EcuM_RequestedState(ECUM_STATE_RUN, ECUM_RUNSTATUS_RELEASED)
The last POST_RUN request is releasedBswM_EcuM_RequestedState(ECUM_STATE_POST_RUN, ECUM_RUNSTATUS_RELEASED)

EcuM does not switch anything by itself. The rules of BswM's mode arbitration decide, and an action list tells EcuM the new state with EcuM_SetState (BswM sets the EcuM state). EcuM then switches the ECU mode the SWCs see through the RTE: STARTUP, RUN, POST_RUN, SLEEP or SHUTDOWN. When the RTE has acknowledged the switch, EcuM confirms the state with BswM_EcuM_CurrentState (EcuM tells BswM its current state).

A RUN request does not stop a shutdown

In EcuM Flex, EcuM has no state machine of its own for RUN and POST_RUN: it relies on the state transitions BswM makes and does not request a state itself. A RUN request is therefore information for BswM's rules, not a lock. When an action list calls EcuM_GoDownHaltPoll (the call that takes the ECU to its shutdown target, the place it goes when it stops: off, reset or sleep), EcuM goes down. The specification defines no check of open RUN requests in that call. Whether open requests hold off a shutdown is decided only by how the BswM rules are written.

This is the main difference from EcuM Fixed (the older EcuM variant with its own fixed state machine, lesson 51), where the RUN requests held the ECU in its RUN state until the last one was released.

    In 4.4.0 EcuM requested the next state instead of reporting a status: when the last RUN request was released it called BswM_EcuM_RequestedState(POST_RUN, ECUM_RUNSTATUS_RELEASED), when the last POST_RUN request was released BswM_EcuM_RequestedState(SHUTDOWN, ECUM_RUNSTATUS_RELEASED). There was no report for the first request. In R19-11 the BswM specification removed BswM_EcuM_RequestedState and BswM_EcuM_CurrentState as obsolete, while the EcuM specification still called them; R20-11 reinstated both. R20-11 has the three reports of this page, but its text names the states ECUM_STATE_APP_RUN and ECUM_STATE_APP_POST_RUN; from R21-11 on they are ECUM_STATE_RUN and ECUM_STATE_POST_RUN, as in EcuM_StateType.

    Things to notice. EcuM only counts and reports; BswM decides. A user that needs POST_RUN time must request it before it releases RUN. The "shut down now" button works even while requests are open: in EcuM Flex nothing in EcuM stops a shutdown that BswM starts.
