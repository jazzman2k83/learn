Network and Mode Management in AUTOSAR Classic

Network Management

The ComM channel state machine

For every channel, ComM runs one state machine. Its three main states are the three communication modes; four sub-states make switching on and off an orderly process.

Lesson 5 showed how a ComM user asks for a communication mode with ComM_RequestComMode. This lesson shows what ComM does with that request: which state the channel is in, what moves it to the next state, and whom ComM calls on the way.

Three main states, one per communication mode

ComM runs one state machine per channel, and each one works independently of the others. On the example ECU, ChassisCan can communicate while BodyCan sleeps. The three main states carry the names of the three communication modes, and each one grants the channel a different capability:

Main stateSendsReceivesNetwork management
COMM_FULL_COMMUNICATIONyesyesbus communication requested
COMM_SILENT_COMMUNICATIONnoyesbus communication released
COMM_NO_COMMUNICATIONnonobus communication released

After initialization every channel is in COMM_NO_COMMUNICATION. ComM does not report this first state to the users, because the RTE is not running yet at that moment. After that, every change of the main state is reported to all users of the channel. The sub-states below stay invisible to the users: they only ever see the three modes.

Whenever the channel enters a main state, ComM asks the bus state manager of the channel (CanSM on a CAN network) for exactly that mode. CanSM switches the controller and transceiver and reports the reached mode back; lesson 21 shows how. COMM_SILENT_COMMUNICATION is never requested by a user: ComM uses it on the way down, so that the ECU still listens while the others finish.

Four sub-states

Two main states are split in two:

inside COMM_NO_COMMUNICATION

COMM_NO_COM_NO_PENDING_REQUEST

The default. Nobody wants the channel. A user request, a wakeup reported by EcuM or active diagnostics moves it on.

inside COMM_NO_COMMUNICATION

COMM_NO_COM_REQUEST_PENDING

Full communication is wanted, but ComM waits until communication allowed (a flag per channel, set by the ECU's mode management once the ECU is ready to communicate on it; lesson 9) is true. Then it switches at once.

inside COMM_FULL_COMMUNICATION

COMM_FULL_COM_NETWORK_REQUESTED

Something in this ECU needs the channel. ComM asks network management to keep the bus awake.

inside COMM_FULL_COMMUNICATION

COMM_FULL_COM_READY_SLEEP

Nothing in this ECU needs the channel any more. ComM has released the network but still communicates, until network management lets the bus sleep.

Why the extra states? If one ECU simply switched its communication off, the others would miss its messages and store errors. COMM_FULL_COM_READY_SLEEP and COMM_SILENT_COMMUNICATION exist to let all ECUs of a bus stop together.

What each step does

Read Figure 1 from the bottom, the way a request travels:

  1. A user requests full communication. The channel goes from COMM_NO_COM_NO_PENDING_REQUEST to COMM_NO_COM_REQUEST_PENDING. The same happens when EcuM reports a wakeup of the channel, or when Dcm reports active diagnostics.
  2. As soon as communication is allowed, the channel enters COMM_FULL_COMMUNICATION, always in COMM_FULL_COM_NETWORK_REQUESTED. ComM asks CanSM for full communication and asks network management to keep the bus awake. After a wakeup without a user request, ComM starts network management passively instead: it joins in without asking for the bus itself.
  3. When no user requests the channel any more (and no diagnostics are active), the channel moves to COMM_FULL_COM_READY_SLEEP and ComM releases the network. A new request brings it straight back.
  4. When network management reports that the bus prepares to sleep, the channel enters COMM_SILENT_COMMUNICATION: the ECU stops sending but still listens.
  5. When network management reports that the bus sleeps, the channel enters COMM_NO_COMMUNICATION. ComM asks CanSM to switch the network off.

From COMM_SILENT_COMMUNICATION there are two ways back up: a user request leads to COMM_FULL_COM_NETWORK_REQUESTED; another ECU that keeps the bus awake again leads to COMM_FULL_COM_READY_SLEEP, because this ECU itself still needs nothing.

Try it

The example ECU's channel ChassisCan with its user UserChassis, and the Brake ECU on the same bus. The dots on the time line are the messages with which network management keeps the bus awake. Timings are small example values on a real-time clock.

Things to try: request the channel and release it again; release it while the Brake ECU still needs the bus; switch communication allowed off and then request.

Things to notice. The users see only three modes; the sub-states are ComM's own business. Releasing the channel does not switch anything off: ComM goes to COMM_FULL_COM_READY_SLEEP and waits for network management. The way down always passes COMM_SILENT_COMMUNICATION, so the ECU listens until the bus really sleeps. A request that arrives while communication is not allowed waits in COMM_NO_COM_REQUEST_PENDING.
