Wakeup validation

A pending wakeup source is not trusted yet. EcuM switches the source on, asks again and again whether the wakeup was real, and gives up when its time runs out.

Lesson 33 showed the four states of a wakeup source. This lesson follows the step from pending to validated or expired, call by call, with the body CAN wakeup of the example ECU.

Why validate

Wakeup events can be produced by accident: an electromagnetic spike on the CAN wires or a bouncing contact on a pin looks like a wakeup to the hardware. If the ECU started its communication on every such event, it would drain the battery. Wakeup validation (checking that a wakeup was real, for example that a valid CAN message follows) waits for proof before the ECU acts.

Validation is configured per wakeup source: a source with a configured validation timeout (how long EcuM waits for proof) is validated, a source without one counts as validated as soon as it is reported. The five predefined sources (power, resets, watchdogs) are never validated. Exactly one module of the basic software confirms a given source, by calling EcuM_ValidateWakeupEvent (the call that tells EcuM a pending wakeup is real); it may be a driver, an interface such as CanIf, a handler or a manager.

The WakeupValidation sequence

EcuM runs the validation in its main function. It does not know how to check a CAN bus or a pin, so it calls three callouts that the integrator writes (they belong to the integration code, not to a module):

once, on pending

EcuM_StartWakeupSources

Switches the source on so that it can deliver the proof. For a CAN source it calls CanSM_StartWakeupSource (CanSM starts the transceiver and controller of the network without full communication).

every main function cycle

EcuM_CheckValidation

Asks the validating module whether the proof has arrived, for CAN with CanIf_CheckValidation. If it has, that module calls EcuM_ValidateWakeupEvent.

once, on expiry

EcuM_StopWakeupSources

Switches the source off again after a failed validation, for CAN with CanSM_StopWakeupSource.

When a source is validated, EcuM does three things: it calls ComM_EcuM_WakeUpIndication for every ComM channel the source names, it calls ComM_EcuM_PNCWakeUpIndication (EcuM tells ComM that a PNC has woken up) for every PNC the source names, and it reports ECUM_WKSTATUS_VALIDATED to BswM with BswM_EcuM_CurrentWakeup. For a source that belongs to a communication channel the validation always has this full effect, whatever phase the ECU is in.

The validation timeout

The timer starts when EcuM_SetWakeupEvent reports the source, and EcuM_ValidateWakeupEvent stops it. A second report of the same source does not restart it. EcuM may run one timer per source, or a single timer that it prolongs to the longest timeout when a new source reports.

When the timer runs out, EcuM marks the source expired, reports ECUM_WKSTATUS_EXPIRED to BswM and calls EcuM_StopWakeupSources. BswM judges the whole validation: it has passed if at least one pending source was validated, and failed if the last timeout expires without one. Because the checks run in the main function, its period should be about half of the shortest validation timeout.

The sequence and its functions are the same in 4.4.0 and R20-11. ComM_EcuM_PNCWakeUpIndication exists since 4.3.0; older releases informed ComM per channel only.

Things to notice. The report (EcuM_SetWakeupEvent) usually comes from an interrupt, the validation from EcuM's main function, cycle after cycle. EcuM never checks a bus itself: the callouts hand the work to CanSM and CanIf. ComM hears of a wakeup only once it is validated.
