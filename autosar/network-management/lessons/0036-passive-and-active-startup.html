Network and Mode Management in AUTOSAR Classic

Network Management

Passive and active startup

A bus can wake because this ECU needs it, or because another ECU does. The wakeup looks the same on the wires, but ComM and NM treat the two starts differently, and so does the moment this ECU lets the bus sleep again.

The example is chassis CAN: the gateway and the Brake ECU. Either the gateway's ComM user UserChassis needs the bus, or the Brake ECU wakes it.

Active wakeup

An active wakeup (a wakeup this ECU starts itself because a local user needs the bus) begins with a request: BodyControl calls ComM_RequestComMode for UserChassis. Once communication allowed is set, ComM enters COMM_FULL_COM_NETWORK_REQUESTED, asks CanSM for full communication and calls Nm_NetworkRequest.

CanNm leaves Bus-Sleep Mode for the Repeat Message State and sends NM PDUs, if configured first with immediate transmission. If the Active Wakeup Bit is enabled, CanNm sets it in its NM PDUs, because it left Bus-Sleep (or Prepare Bus-Sleep) Mode through a network request; it clears the bit when it leaves Network Mode. The other ECUs wake up passively. After the Repeat Message Time the gateway, still requesting the network, goes to the Normal Operation State and keeps the bus awake.

Passive wakeup

A passive wakeup (a wakeup by another ECU through the bus; this ECU joins without requesting the network) reaches ComM in one of two ways:

through EcuM

A validated wakeup

The transceiver woke the sleeping ECU, EcuM validated it (lesson 35) and called ComM_EcuM_WakeUpIndication. ComM goes through COMM_NO_COM_REQUEST_PENDING to full communication.

through NM

An NM PDU in Bus-Sleep Mode

CanNm is in Bus-Sleep Mode but still receives an NM PDU, for example when another node sends from Prepare Bus-Sleep Mode just after this one fell asleep. CanNm calls Nm_NetworkStartIndication, NmIf forwards ComM_Nm_NetworkStartIndication, and ComM switches to full communication if communication is allowed.

Either way ComM enters COMM_FULL_COM_NETWORK_REQUESTED and calls Nm_PassiveStartUp instead of Nm_NetworkRequest. CanNm enters the Repeat Message State and sends NM PDUs for the Repeat Message Time, so that the others see it, but without the Active Wakeup Bit. Then, because the network is not requested, it goes to the Ready Sleep State: it stops sending and stays awake only as long as other ECUs send.

Does ComM go to ready sleep on a passive wakeup?

Yes. With the NM variant FULL (all three channels of the gateway), ComM leaves COMM_FULL_COM_NETWORK_REQUESTED for COMM_FULL_COM_READY_SLEEP as soon as no ComM user requests full communication and Dcm reports no active diagnostics. On entering it, ComM calls Nm_NetworkRelease. ComM needs no timer of its own here: NM's Repeat Message Time already keeps the bus awake for a minimum time. With the variants LIGHT and NONE, ComM instead stays in network requested until a configured minimum full-communication time has passed.

If UserChassis requests the bus later, ComM goes back to network requested and calls Nm_NetworkRequest: CanNm moves from Ready Sleep to Normal Operation. If the channel belongs to an NM coordination cluster (buses that the NM coordinator keeps awake and puts to sleep together, lesson 37), NmIf treats Nm_PassiveStartUp of that channel like a network request. The example gateway has no such cluster: it uses partial networking in NmIf, and in R25-11 an NmIf supports either that or the NM coordinator (lesson 3).

Try it

Compare the three starts on chassis CAN. The rows are in time order; the timings are not to scale.

Things to notice. The difference lies in one call: Nm_NetworkRequest or Nm_PassiveStartUp. Both put CanNm into the Repeat Message State and make it send, so every wakeup is visible on the bus. Only an active wakeup sets the Active Wakeup Bit and keeps the bus awake after the Repeat Message Time; a passive one follows the others.
