Network and Mode Management in AUTOSAR Classic

Network Management

The CanNm states

CanNm runs the coordination algorithm of lesson 12 on one CAN network. It does so with three modes and, inside the first one, three states. This lesson walks through all of them.

Each node runs its own copy of this state machine. It sees only two things: whether its own ECU needs the bus (the network is requested or released) and the NM PDUs it sends and receives. From these alone, all nodes of the bus reach the same decision.

Three modes

awake

Network Mode

Network Mode (the mode in which the bus is awake; it holds three states). The node takes part in communication.

calming down

Prepare Bus-Sleep Mode

Prepare Bus-Sleep Mode (the bus is quietening down: queued messages are sent, then no node sends any more). It lasts a fixed wait.

asleep

Bus-Sleep Mode

Bus-Sleep Mode (the bus sleeps; controller and transceiver can go into low-power modes). After initialization CanNm is here.

CanNm reports every change of mode upward: through NmIf to ComM. Entering Network Mode, Prepare Bus-Sleep Mode or Bus-Sleep Mode each has its own report; lesson 6 showed what ComM does with them.

Three states inside Network Mode

entered first

Repeat Message State

Repeat Message State (the node sends NM PDUs for a fixed time, so that every other node sees it). Every entry into Network Mode starts here. It also keeps a node awake for a minimum time.

network requested

Normal Operation State

Normal Operation State (the node needs the bus and keeps sending NM PDUs). It lasts as long as the network is requested.

network released

Ready Sleep State

Ready Sleep State (the node no longer needs the bus and stops sending, but stays awake while others still send). It waits for the bus to fall silent.

Requested and released

Next to the states, CanNm keeps a second, parallel piece of information: the network is either requested or released. ComM requests the network when a channel enters COMM_FULL_COM_NETWORK_REQUESTED and releases it in COMM_FULL_COM_READY_SLEEP. After initialization it is released.

  • When the Repeat Message State ends, the node goes to the Normal Operation State if the network is requested, otherwise to the Ready Sleep State.
  • Released in the Normal Operation State: the node goes to the Ready Sleep State and stops sending NM PDUs.
  • Requested in the Ready Sleep State: the node goes back to the Normal Operation State and starts sending again at once.

Released does not mean asleep. In the Ready Sleep State the node still communicates; it just no longer votes for staying awake.

The way down and the way back

A node in the Ready Sleep State waits until no NM PDU has been seen for the NM-Timeout Time (a timer restarted by every NM PDU sent or received; lesson 14). Each NM PDU of another node restarts it. When it runs out, the node enters Prepare Bus-Sleep Mode and stays there for the Wait Bus-Sleep Time (the length of the calm-down phase; lesson 14). Then it enters Bus-Sleep Mode. Because all nodes see the same last NM PDU and use the same times, they fall asleep at about the same moment.

Three things bring a node back into Network Mode, always into the Repeat Message State:

  • its own ECU requests the network, in Bus-Sleep Mode or in Prepare Bus-Sleep Mode;
  • a passive startup (the node joins the network without requesting it, typically after a wakeup by another node), in either of these modes;
  • an NM PDU received in Prepare Bus-Sleep Mode: another node still or again needs the bus.

An NM PDU received in Bus-Sleep Mode is different. CanNm does not wake up by itself: it only reports the received PDU upward (as a network start indication) and leaves the decision to ComM and the ECU's mode management. Whether the ECU may communicate at that moment depends on where it is in its startup or shutdown.

In 4.4.0, Prepare Bus-Sleep Mode always ends after the Wait Bus-Sleep Time. From R19-11 on (so also in R20-11), a node can be configured to stay in Prepare Bus-Sleep Mode until it is powered off or a reason to restart applies.

Try it

The example ECU's channel ChassisCan and the Brake ECU. Request and release the network through UserChassis, let the Brake ECU keep the bus awake, or let it wake the bus for a short time. Timings are small example values on a real-time clock.

Things to try: wake the bus by the Brake ECU and watch the gateway pass through the Repeat Message State although nobody on it requests the network. Release the user while the Brake ECU still sends, then switch the Brake ECU off. Request again during Prepare Bus-Sleep Mode.

Things to notice. Every entry into Network Mode goes through the Repeat Message State, so every node that wakes is seen by the others. A node that no longer needs the bus stops sending, but only the silence of all nodes moves it towards sleep. In Bus-Sleep Mode a received NM PDU is only reported; the ECU decides whether to wake.
