Network and Mode Management in AUTOSAR Classic

Network Management

Remote sleep, car wakeup and user data

The NM PDU can tell a node more than "someone is still awake": that all the others are ready to sleep, that the whole car should wake up, or whatever the application puts into the user data.

This lesson collects four optional features of CanNm and UdpNm. Each of them is switched on in the configuration; without them, NM behaves as in lessons 13 and 14.

Remote Sleep Indication

A node in Normal Operation State keeps the bus awake. It may want to know whether it is the only one that still does. The Remote Sleep Indication (the notification that no other node has sent an NM PDU for a while: all the others are ready to sleep) answers that:

  • If the node receives no NM PDU in Normal Operation State for the Remote Sleep Indication Time (a configured time of silence from the other nodes), CanNm calls Nm_RemoteSleepIndication.
  • If, after that, an NM PDU arrives again in Normal Operation State or Ready Sleep State, or the node enters Repeat Message State from one of them, CanNm calls the Remote Sleep Cancellation (the notification that at least one other node is not ready to sleep any more), Nm_RemoteSleepCancellation.

The node itself still needs the bus, so it goes on sending and the bus stays awake. NmIf does not pass these notifications on to ComM: they are only needed inside NmIf, by the NM coordinator (a gateway function that keeps several buses awake together and shuts them down together; lesson 37). An upper layer can also ask for the current status, but not in Repeat Message State, Prepare Bus-Sleep Mode or Bus-Sleep Mode.

Car wakeup

Car wakeup (an NM feature with which one ECU asks for the whole vehicle to wake up, through a bit in its NM PDU) is built on top of the user data. The position of the car wakeup bit, a byte and a bit within the NM PDU, is configured; setting it on the sending side is the application's job, through the normal user data path.

On reception CanNm checks the bit in every NM PDU. If car wakeup reception is enabled and the bit is 1, CanNm calls Nm_CarWakeUpIndication and then handles the PDU as usual. With a filter enabled, only NM PDUs from one configured Source Node Identifier count; a sub-gateway uses this to follow only the central gateway and to avoid wrong wakeups. During the indication the whole received PDU can be read, so the receiver can see who sent the request. The part that handles the request passes it to its other networks by setting the bit in its own NM PDUs, and drops it when the sender does not repeat it within a certain time.

State change notification

With the state change notification (an option in which CanNm reports each change of its state with the previous and the new state) switched on, CanNm calls Nm_StateChangeNotification on every state change. NmIf passes it on to BswM, so that BswM rules can react to NM states. Optionally NmIf also writes a 6-bit COM signal that is meant to be part of the node's own NM PDU, so that the other nodes see why this node is awake:

In 4.4.0 NmIf did not call BswM on a state change; it only wrote the optional COM signal. The call to BswM is in R20-11.

User data through COM

The user data can be set in two ways: through the NM API (NmIf passes it to CanNm), or through COM. With the COM way switched on, the user data bytes are one I-PDU of COM, with ordinary signals in it, and the API for setting user data is not available. CanNm fetches the I-PDU from COM through PduR each time before it sends an NM PDU and combines it with the system bytes and the PNC bit vector. If COM itself sends that I-PDU, PduR passes it to CanNm, which sends an extra NM PDU with the new data, but only in Repeat Message State or Normal Operation State.

The way back is different: the user data of received NM PDUs can only be read through the NM API, not as COM signals. And user data travels only with NM PDUs: it is always sent in Repeat Message State, in Normal Operation State only when this node sends (see bus load reduction), and never in Ready Sleep State.

Things to notice. Remote sleep is a view from one awake node: it sends, the others are silent. It does not change any state and is not passed to ComM. Car wakeup and the state report travel in the user data, so they depend on a node actually sending NM PDUs. COM user data is fetched by CanNm just before each transmission: COM decides the content, CanNm the timing.
