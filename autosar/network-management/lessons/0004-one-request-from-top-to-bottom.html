Network and Mode Management in AUTOSAR Classic

Network Management

One request from top to bottom

The SWC BodyControl of the body gateway needs the Comfort functions. One call through the RTE sets off work in ComM, CanSM, NmIf, CanNm and BswM, until body CAN is running and the Comfort I-PDUs flow.

This lesson follows that one request call by call. Each module is explained in its own part later; here the aim is the order, and which code runs when.

Where the work happens

Most of the calls below do not do their work at once. They store a request, and a main function (a function of a module that the scheduler calls cyclically; timers and state machines advance in it) does the work later. ComM has one main function per channel, ComM_MainFunction_BodyCan for body CAN; CanSM and CanNm have one each. In the diagram, every grey band starts a new execution context: the runnable of the SWC in its task, then the main functions one after the other, and the callbacks of the CAN driver.

The starting point: the gateway is running, body CAN sleeps, and BswM has already set communication allowed (a flag per channel that BswM sets in ComM; ComM switches a channel on only while it is TRUE) for BodyCan.

The three phases

ComM

Request, then decide in the main function

ComM_RequestComMode (the ComM API with which a ComM user, a logical requester of communication, asks for a mode) only stores the request. In its main function ComM moves PNC Comfort to COMM_PNC_REQUESTED (the PNC is needed by a local user), and then switches the channel BodyCan (ComM's name for body CAN) to COMM_FULL_COMMUNICATION (the channel sends and receives).

two paths down

Hardware and network management

On entering full communication ComM asks CanSM for the mode, and on entering COMM_FULL_COM_NETWORK_REQUESTED (the part of full communication in which a user needs the channel) it requests the network with Nm_NetworkRequest (ComM asks NM to keep the bus awake). CanSM switches transceiver and controller on; CanNm starts sending NM PDUs.

back up

Indications, then BswM switches COM

When the controller runs, CanSM reports full communication to ComM and BswM. ComM passes the mode on to BswM and to the user's port. A BswM rule then starts the I-PDU groups of body CAN in COM.

The NM message on the bus

CanNm leaves Bus-Sleep Mode (the CanNm mode in which the bus sleeps) and enters Network Mode (the mode in which the network is awake) in its Repeat Message State (the first state of Network Mode, in which the node makes itself seen by sending NM PDUs). From then on it sends an NM PDU (the NM message an ECU sends while it needs the bus) cyclically. ComM has also put the bit of PNC 16 into the IRA (internal request array: one bit per PNC that this ECU requests itself) of BodyCan with Nm_UpdateIRA, so the NM PDUs carry the Comfort request to the Door ECU.

The same happens on Ethernet, because PNC Comfort also uses Eth: in ComM_MainFunction_Eth ComM requests the mode from EthSM and the network through NmIf from UdpNm. Lessons 23 and 24 follow that path.

Up to R20-11 (and in 4.4.0) ComM did not pass PNC requests with Nm_UpdateIRA. It wrote them into a COM signal that was packed into the NM PDU, and read the received PNC requests from COM signals as well (lesson 53). The path through NmIf came as draft in R21-11 and replaced the COM path in R22-11.

In 4.4.0 and R20-11 CanNm sends its NM PDU by calling CanIf_Transmit directly; R25-11 places the L-SDU Router between them (LSduR_CanNmTransmit, marked draft).

Up to R24-11 the mode indication that CanSM calls in ComM is ComM_BusSM_ModeIndication, one name for every bus state manager. R25-11 ComM names it ComM_CanSM_ModeIndication on CAN; the R25-11 CanSM text still uses the old name (lesson 21).

Things to notice. The SWC's call returns at once; nothing on the bus has changed yet. ComM requests CanSM before it requests NM, and both in the same main function call. The reached mode travels back up by indications: CanSM to ComM and BswM, ComM to BswM and the RTE. BswM, not ComM, starts the I-PDU groups.
