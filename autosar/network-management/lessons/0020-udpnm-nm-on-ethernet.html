Network Management

UdpNm: NM on Ethernet

UdpNm runs the same algorithm as CanNm, with the same states, timers and NM PDU. What changes is the way down: the NM PDU travels as the payload of a UDP packet, through the socket layer instead of CanIf.

On the example ECU, the channel Eth (network handle 2) connects the gateway to the Head unit, with UdpNm as its bus NM. This lesson lists what stays as on body CAN and checks each difference against the UdpNm specification.

The same algorithm

UdpNm is a decentralized NM like CanNm: every node decides from the NM PDUs it sends and receives. It has the same three modes (Network Mode with Repeat Message State, Normal Operation State and Ready Sleep State; Prepare Bus-Sleep Mode; Bus-Sleep Mode), the same timers (NM-Timeout Time, Repeat Message Time, Wait Bus-Sleep Time, Message Cycle Time) and the same NM PDU layout: Source Node Identifier and Control Bit Vector in byte 0 and byte 1 by default, then user data and the PNC bit vector. The Ethernet NM PDU is not limited to 8 bytes; its length is configured.

Most optional features exist on both: immediate transmissions, node detection, user data through the API or through COM, passive mode, communication control, remote sleep, car wakeup, state change notification and partial networking. Above them, NmIf calls UdpNm_NetworkRequest where it would call CanNm_NetworkRequest, and ComM does not notice the difference.

What is different

CanNm on body CANUdpNm on Ethernet
Layer belowCanIf: CanNm sends through it and gets CanNm_RxIndication from itSoAd (Socket Adaptor: maps PDUs to sockets of the TCP/IP stack): UdpNm sends with SoAd_IfTransmit and receives through UdpNm_SoAdIfRxIndication
On the wirethe NM PDU is one CAN framethe NM PDU is the payload of an NM packet (an Ethernet frame with an IP and a UDP header around the NM PDU)
Reaching every nodeevery frame reaches every node of the busall UdpNm instances of one NM cluster use the same UDP receive port; the addressing of the packets is part of the SoAd socket configuration
Bus load reductionoptionalnot specified for UdpNm
Transmit confirmationa real confirmation from CanIf, or optionally an immediate one; with partial networking a transmit timeout can be monitoredno real confirmation is available from SoAd or TcpIp: each accepted transmit request counts as sent; no transmit timeout monitoring
First NM PDU after wakeupas in lesson 14optionally repeated in every main function until SoAd accepts it, because the transmission path may not be ready yet

The last row is the one that matters most in practice. On Ethernet, EthSM has to enable the transmission path before anything can be sent (lessons 23 and 24). If UdpNm starts Network Mode quickly, SoAd may refuse its first NM PDU. UdpNm then simply asks again in its next main function: always for the burst of immediate transmissions, and for the first NM PDU when the option to retry it is switched on.

Try it

Step through the first NM PDU on Eth after ComM has requested the network, with immediate transmissions configured. The Head unit stands for the whole other ECU.

Things to notice. Nothing above UdpNm changes on Ethernet: the same states, timers and NmIf calls as on CAN. The differences all sit at the bottom edge of UdpNm: SoAd instead of CanIf, no real transmit confirmation, no bus load reduction, and a first NM PDU that may have to wait for the transmission path.
