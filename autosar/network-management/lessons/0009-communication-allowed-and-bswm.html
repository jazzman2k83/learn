Network and Mode Management in AUTOSAR Classic

Network Management

Communication allowed, and BswM

A request alone does not switch a channel on. ComM also waits until BswM says that communication on the channel is allowed, and once the channel communicates, BswM starts the I-PDUs that belong to it.

This lesson shows the two places where ComM and BswM meet: the flag that lets a channel leave no communication, and the reaction of BswM when a channel reaches full communication.

A second condition for leaving no communication

ComM keeps one communication allowed flag (a flag per channel that BswM sets; ComM leaves no communication only while it is TRUE) for every channel. After ComM is initialized, every flag is FALSE.

When a ComM user requests full communication on a channel in COMM_NO_COM_NO_PENDING_REQUEST, the channel moves to COMM_NO_COM_REQUEST_PENDING. There it waits for the flag. As soon as the flag is TRUE, the channel switches to COMM_FULL_COMMUNICATION. If the request is withdrawn before that, the channel goes back to COMM_NO_COM_NO_PENDING_REQUEST.

ComM reads the flag only in COMM_NO_COM_REQUEST_PENDING. Setting it to FALSE while the channel is in full communication has no visible effect: the channel does not drop to no communication. The flag is a gate on the way up, not a switch that turns the channel off.

BswM sets the flag

The flag is set through ComM_CommunicationAllowed (the ComM function that sets communication allowed for one channel to TRUE or FALSE). With the ECU State Manager of R25-11, BswM calls it. BswM does this only because it is configured to: one of its rules (a configured condition on the modes BswM knows, evaluated to true or false) starts an action list (the configured actions BswM executes for a rule result) that contains the action "allow communication for channel X".

The idea is that communication is allowed once the ECU has started, or has woken up and finished its checks of the wakeup, so that the channel can work reliably. On the body gateway, the action lists of BswM allow BodyCan, ChassisCan and Eth at that point. Lesson 27 shows how such rules are built.

When the channel reaches full communication

ComM does not touch the I-PDUs of COM itself. It reports every change of the main state of a channel to BswM, and the bus state manager reports the mode the bus has actually reached, which ComM passes on to its users and to BswM. A BswM rule on "channel ChassisCan is in COMM_FULL_COMMUNICATION" can then start the I-PDU groups of chassis CAN in COM, and a rule on silent or no communication stops them again.

Try it

Switch the request of UserChassis and the flag for ChassisCan on and off, in either order. Going to sleep is shortened here: assume the other ECUs on chassis CAN are already done.

ChassisCan I-PDU groups

Things to notice. Order does not matter on the way up: request first and the channel waits in COMM_NO_COM_REQUEST_PENDING; allow first and the request goes straight through. Withdrawing the flag later changes nothing. The I-PDU groups follow the channel only because a BswM rule makes them.
