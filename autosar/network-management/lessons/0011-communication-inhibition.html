Network Management

Communication inhibition

Sometimes a request for communication must not be obeyed: a faulty input keeps waking the whole car, or one ECU keeps a bus awake for no reason. ComM can then ignore or override the requests of its users for a channel.

This lesson shows the two kinds of inhibition, how an ECU decides which of them may be used, how rejected requests are counted, and the one exception: diagnostics.

Two kinds of inhibition

Communication inhibition (the ComM functions that limit what the requests of ComM users can do to a channel) comes in two kinds. Each can be switched on and off at run time and per channel. It is requested through ComM functions by a privileged SWC or by OEM-specific basic software, never by an ordinary ComM user, and ComM never uses it on its own initiative.

do not wake the bus

Wake up inhibition

With wake up inhibition (requests for full communication are not executed while the channel is in no or silent communication) ComM accepts a user's request but does not execute it, so the channel is not woken. A channel that is already in full communication is not affected. The request is kept: when the inhibition is switched off, it is executed. Typical use: a wakeup line has been found faulty, or the vehicle is in transport mode.

take the bus down

Limit to no communication

With limit to COMM_NO_COMMUNICATION (requests for full communication are ignored and an actively requested channel is taken down) a channel in COMM_FULL_COM_NETWORK_REQUESTED goes to COMM_FULL_COM_READY_SLEEP despite its users, and from there to no communication. All requests for full communication are ignored, and once the channel is in no communication they are cleared: when the limit is lifted, the users must request again. It can be set for one channel or for the whole ECU.

Neither kind blocks a passive wakeup (the ECU is woken from outside, for example by a message on the bus): ComM must always be able to follow a bus that another ECU wakes. For the same reason the limit does nothing to a channel that is kept awake only by the other ECUs. Optionally, ComM asks for a reset of the ECU after it has forced a channel down, for the case that a faulty user would keep its request forever.

ECU group classification

Whether the inhibitions may be used at all is decided by the ECU group classification (a small bit field per ECU that enables each kind of inhibition). Bit 0 enables wake up inhibition, bit 1 enables the limit to no communication; the configured default is 3, both enabled. If a function is called for a kind whose bit is not set, ComM refuses the call. The classification can be changed at run time, for example by a diagnostic service; such a change does not cancel an inhibition that is already active.

Counting rejected requests

A user whose request is rejected gets COMM_E_MODE_LIMITATION (the return value of ComM_RequestComMode when the mode cannot be granted because of inhibition). For wake up inhibition, which keeps the request but does not execute it, the specification does not say separately which value the call returns; the simulation below returns COMM_E_MODE_LIMITATION there too. ComM also counts these requests in one counter for the whole ECU, the Inhibited Full Communication Request Counter (the number of requests for full communication that inhibition has rejected). It counts from 0 to 65535 and then stops, can be kept in non-volatile memory, and can be read and reset, for example by a diagnostic service. It helps to find software that keeps trying to wake the bus without a good reason.

The diagnostic exception

While a diagnostic session is active, communication inhibition is suspended. As long as Dcm reports active diagnostics through ComM_DCM_ActiveDiagnostic, the channel is requested and the limit does not take it down; the ECU must not fall asleep under the tester. When Dcm reports ComM_DCM_InactiveDiagnostic, the inhibitions apply again.

4.4.0 and R20-11 contradict themselves on the wake up inhibition status: one requirement says it must always be stored in non-volatile memory, while a per-channel configuration switch, already present in these releases, decides whether it is stored. The ECU group classification is listed among the data ComM keeps in non-volatile memory. R25-11 resolves this: both are stored only where the configuration says so; otherwise the configured defaults apply again after a reset.

Things to notice. Wake up inhibition keeps a request and executes it later; the limit throws requests away. Wake up inhibition never stops a channel that is already up, the limit does exactly that. The classification only decides whether an inhibition may be switched on. Active diagnostics overrides both.
