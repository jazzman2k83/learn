Network and Mode Management in AUTOSAR Classic

Network Management

The NM PDU

Every NM PDU says three things: who sent it, a few control flags, and, on a bus with partial networking, which PNCs the sender requests. The rest of its bytes are free for the application.

Lessons 13 and 14 used the NM PDU only as a signal: it arrives, and the NM-Timeout Time starts again. This lesson opens it. It shows the four parts of the PDU in a simple view; the meaning of each single control bit follows in lesson 57.

Four parts in one PDU

The CanNm specification shows an NM PDU of 8 bytes, the length of a classic CAN frame. Its bytes fall into four parts. The first two are the system bytes, which CanNm fills itself:

system byte

Source Node Identifier

The Source Node Identifier (the node identifier of the sending ECU, one byte, unique in the bus) tells every receiver who sent the PDU. CanNm writes the configured identifier of its own node into it.

system byte

Control Bit Vector

The Control Bit Vector (one byte of control bits that switch NM features on the receivers) carries flags such as "please repeat your NM PDUs" or "I woke the bus". CanNm sets it to 0x00 at initialization and changes single bits when a feature needs them.

partial networking

PNC bit vector

The PNC bit vector (one bit per PNC; a bit at 1 means the sender requests that PNC) is only present when partial networking is used on the bus. The bits come from ComM's PNC requests through NmIf.

free bytes

User data

User data (bytes of the NM PDU that the application fills; NM itself does not interpret them) takes every byte that is neither a system byte nor part of the PNC bit vector. At initialization each user data byte is 0xFF.

Neither system byte has to be there. Each one can sit in byte 0 or byte 1, or be left out; a byte left out becomes another byte for user data or the PNC bit vector. Partial networking needs the Control Bit Vector, because one of its bits tells the receivers that a PNC bit vector is present.

The example ECU's NM PDU

On body CAN the gateway puts the Source Node Identifier in byte 0 and the Control Bit Vector in byte 1. The UdpNm specification marks this layout as the default; the CanNm specification has no default, and the example table of the NM protocol specification shows the two bytes the other way round. The PNC bit vector starts right after the system bytes, at an offset of 2 bytes. In this course the PNC bit vector of body CAN is one byte long, so bytes 3 to 7 are user data.

The offset decides which PNC owns which bit. The byte of a PNC inside the PNC bit vector is its number divided by 8, minus the offset; the bit is the remainder. Comfort (PNC 16) is therefore bit 0 and Lighting (PNC 17) bit 1 of the first byte of the PNC bit vector, which is byte 2 of the PDU. With an offset of 2 there is no bit for PNCs 0 to 15, and a one-byte vector covers PNCs 16 to 23.

The Door ECU (Source Node Identifier 0x21) and the Light ECU (0x22) send the same layout. The nodes of one bus need the same layout, because each of them reads the NM PDUs of all the others.

The control bits in short

Most bits of the Control Bit Vector belong to features that later lessons explain: the Repeat Message Request (asks all nodes to send their NM PDUs again; lesson 16), the NM Coordinator Sleep Ready Bit (a gateway announces a coordinated shutdown; lesson 39), the PN Shutdown Request Bit (announces that PNCs are released together; lesson 45) and the Partial Network Learning Bit (starts the learning of PNCs; lesson 46). Two of them matter already now:

  • The Partial Network Information Bit (the control bit that says the NM PDU carries a PNC bit vector) is always 1 in the NM PDUs a node sends when partial networking is enabled for it, and 0 otherwise. That is why the gateway's Control Bit Vector reads 0x40 in the panel.
  • The Active Wakeup Bit (a control bit set while the sender is in Network Mode because it requested the network itself) is set when CanNm enters Network Mode from Bus-Sleep Mode or Prepare Bus-Sleep Mode because of a network request, and cleared when CanNm leaves Network Mode again. It is optional and must be enabled in the configuration.

In 4.4.0 the Control Bit Vector had no Partial Network Learning Bit and no PN Shutdown Request Bit; those bit positions were reserved. In 4.4.0 and R20-11 the place of the PNC bit vector (called the PN Info Range there) was configured in CanNm and UdpNm, not in NmIf. The R20-11 Control Bit Vector already has both newer bits, the PN Shutdown Request Bit as a draft.

Things to notice. CanNm fills only the two system bytes; the PNC bit vector comes from ComM through NmIf, and the user data from the application. The layout is configured, so all nodes of one bus must use the same one. With partial networking the PNC numbers and the PNC bit vector offset must match: PNC 16 is bit 0 of the first vector byte only because the offset is 2.
