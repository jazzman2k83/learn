Network and Mode Management in AUTOSAR Classic

Network Management

BswM as the glue

The modules of this course do not call each other for every decision. They report their states to BswM, and BswM's configured rules call the next step: allow communication, start I-PDU groups, put the ECU to sleep.

What goes in

BswM's inputs are a mode request (an input to BswM, typically from an SWC or Dcm, asking for a mode) or a mode indication (an input to BswM from a BSW module reporting its current state). BswM treats both the same way. The modules of this course give it these:

FromReportsCall
EcuMthe state of each wakeup source (a source of wakeups such as ECUM_WKSOURCE_BODYCAN); the result of the RUN requestsBswM_EcuM_CurrentWakeup, BswM_EcuM_RequestedState
ComMthe communication mode of each channel, the mode of each PNCBswM_ComM_CurrentMode, BswM_ComM_CurrentPNCMode
NmIfa state change of the NM of a channelBswM_Nm_StateChangeNotification
CanSM, EthSMtheir own states, such as a bus-off or an EthSM sub-stateBswM_CanSM_CurrentState, BswM_EthSM_CurrentState
SWCs and other requestersrequested modesRTE ports, BswM_RequestMode

Each input is configured as immediate or deferred. An immediate one is evaluated at once, in the context of the caller; a deferred one waits for BswM's main function.

Rules and action lists

A rule is a configured mode arbitration (BswM's evaluation of a rule: a logical expression over the current requests and indications, true or false). The expression combines conditions such as "the mode of ChassisCan equals COMM_FULL_COMMUNICATION" with AND, OR, XOR, NOT and NAND. Rules may not use the results of other rules.

For each rule, BswM can run an action list (the ordered actions BswM runs for a rule result) when it is true and another when it is false. A list is either triggered, running only when the result changes, or conditional, running every time the rule gives that result. An action list may contain actions, other action lists and further rules. BswM does not wait for the result of its actions: the modules report their new states back as indications, and those feed the next rules.

Typical actions

ComM

Allow communication

ComM_CommunicationAllowed for a channel (lesson 9), and ComM_RequestComMode for a ComM user that the configuration gives to BswM: BswM itself can keep a channel requested.

COM

Switch I-PDU groups

Start and stop I-PDU groups in COM (Com_IpduGroupStart, Com_IpduGroupStop) when a channel enters or leaves full communication; similar actions switch deadline monitoring.

EcuM

Shut down or sleep

EcuM_SelectShutdownTarget (selects where the next shutdown leads: off, reset or a sleep mode), then EcuM_GoDownHaltPoll (carries out the selected shutdown target).

startup

Initialize the rest

An EcuM driver init list for the BSW initialized by BswM, Rte_Start, and user callouts for anything else (lesson 26).

BswM can do much more, for example control Service Discovery or switch Ethernet switch port groups; this course uses it only as the glue between the modules shown here.

Try it: three rules of the example ECU

Change the inputs and watch which action lists run. Every change is evaluated at once (as for immediate inputs); Run BswM main function evaluates all rules again, as for deferred inputs. All three action lists are triggered by default; switch the second rule to conditional to see the difference.

    The NM state change notification to BswM (BswM_Nm_StateChangeNotification) exists since R20-11; in 4.4.0 BswM gets no input from NmIf. The other inputs and actions of this lesson are the same in 4.4.0 and R20-11.

    Things to notice. No module of this course calls ComM_CommunicationAllowed or EcuM_GoDownHaltPoll by itself: a BswM rule does, on the states the modules report. A triggered list runs once per change of the result; a conditional one runs at every evaluation with that result. Going to sleep is just a rule: all channels in no communication and no RUN request left.
