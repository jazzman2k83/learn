Network and Mode Management in AUTOSAR Classic

Network Management

Network requested and ready sleep

Inside COMM_FULL_COMMUNICATION, ComM only decides whether this ECU still needs the bus. Whether the bus stays awake is decided together with the other ECUs, by network management.

Lesson 6 introduced the two sub-states of full communication. This lesson looks at the line between them: what keeps a channel in COMM_FULL_COM_NETWORK_REQUESTED, what happens in COMM_FULL_COM_READY_SLEEP, and why the bus can stay awake long after the last ComM user has let go.

What keeps a channel in network requested

The channel stays in COMM_FULL_COM_NETWORK_REQUESTED as long as at least one of these holds:

a ComM user

A user requests full communication

On the example ECU, UserChassis of the SWC BodyControl requests ChassisCan. Several users of one channel are combined: the highest request wins.

diagnostics

Dcm reports active diagnostics

Dcm is not a ComM user. It tells ComM with ComM_DCM_ActiveDiagnostic (Dcm's report that a diagnostic session needs the channel; lesson 10) that a tester is talking to the ECU.

only without network management

A minimum time has not passed

On a channel where ComM does not use network management, ComM keeps the channel requested for a configured minimum time after it was entered.

On entering this sub-state, ComM asks network management to keep the bus awake for this ECU. Nothing else in ComM does that: a request of a user only reaches the bus through this sub-state.

Ready sleep: released, but still awake

When none of the reasons holds any more, the channel moves to COMM_FULL_COM_READY_SLEEP and ComM releases the network. This does not switch anything off. The channel stays in COMM_FULL_COMMUNICATION: the ECU keeps sending and receiving, and the users still see full communication.

From now on network management decides. It keeps the bus awake while any other ECU still needs it, then lets all of them go to sleep together after a short wait. Only then does ComM follow: COMM_SILENT_COMMUNICATION when the bus prepares to sleep, COMM_NO_COMMUNICATION when it sleeps.

Coming back

A new request while the bus is still awake is cheap. In COMM_FULL_COM_READY_SLEEP, a user request (or active diagnostics) brings the channel straight back to COMM_FULL_COM_NETWORK_REQUESTED, and ComM requests the network again; the bus never went down. In COMM_SILENT_COMMUNICATION, a user request leads back into full communication and network requested as well.

A request can also come too late. If the other ECUs have already agreed to sleep, network management reports that the bus sleeps, and the channel drops to COMM_NO_COMMUNICATION even from full communication. The still pending request then starts the channel again from there, as a new wakeup of the bus.

The minimum full-communication time

Right after a wakeup or a power-on, the ECU may need a moment before its applications send their first requests. If the channel fell back to sleep in that moment, it would toggle between no and full communication. Two mechanisms prevent this:

  • On a channel with network management, network management itself keeps the bus awake for a minimum time after it starts (lesson 13 shows the state that does this). ComM needs no timer of its own there.
  • On a channel where ComM does not use network management (lesson 8 shows these variants), ComM starts a timer when it enters COMM_FULL_COM_NETWORK_REQUESTED and keeps the channel there until the timer has expired, even without any request.

Try it

The channel starts awake, requested by UserChassis. Switch the Brake ECU on, then release the channel, and watch how long ComM stays in ready sleep. Timings are small example values on a real-time clock.

Things to notice. ComM answers one question only: does this ECU still need the bus? The answer moves the channel between COMM_FULL_COM_NETWORK_REQUESTED and COMM_FULL_COM_READY_SLEEP. When the bus really sleeps is decided by network management, together with the other ECUs. Ready sleep is still full communication for the users.
