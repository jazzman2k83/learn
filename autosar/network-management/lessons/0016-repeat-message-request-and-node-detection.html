Network Management

Repeat message request and node detection

A node that is awake but no longer needs the bus stays silent. One control bit in the NM PDU makes every node on the bus speak up again for a while, so that each one can be seen by its Source Node Identifier.

Lesson 13 showed that a node in Ready Sleep State sends no NM PDUs. From the bus alone, nobody can tell whether such a node is there. This lesson shows the bit that changes that and the feature built on it.

One bit that sends everyone back

The Repeat Message Request (the control bit that asks every node to go to Repeat Message State) is one bit of the Control Bit Vector. It works in two directions, on every node where the feature of the next section, node detection, is switched on:

sending it

The node that asks

A node in Normal Operation State or Ready Sleep State gets a request to repeat. Its CanNm sets the bit and enters Repeat Message State, so it sends NM PDUs with the bit set. In Repeat Message State, Prepare Bus-Sleep Mode or Bus-Sleep Mode the request is refused.

receiving it

Every other node

A node in Normal Operation State or Ready Sleep State that receives an NM PDU with the bit set enters Repeat Message State as well. There it sends NM PDUs again, even if it had released the network.

Each node stays in Repeat Message State for its Repeat Message Time, then goes on as lesson 13 showed: to Normal Operation State if its network is requested, to Ready Sleep State if it is released. The node that asked clears the bit when it leaves Repeat Message State. Until then it keeps sending the bit in every NM PDU, so a single lost PDU does not stop the request.

The request comes from above NM. NmIf offers it as Nm_RepeatMessageRequest, which ComM does not use; it is meant for extensions of the NM stack, for example an application that wants to know the nodes on the bus.

Node detection

Node detection (finding out which nodes are on the bus by making all of them send) is the use the specification names for this bit. It is an optional feature, switched on per channel. For it to work, the NM PDU must carry a Control Bit Vector (for the bit) and a Source Node Identifier (to tell the senders apart).

While all nodes are in Repeat Message State, every one of them sends NM PDUs with its own Source Node Identifier. The asking node reads the identifier of each received NM PDU. NmIf can also report the first NM PDU that arrives with the bit set, once per stay in Repeat Message State. AUTOSAR does not define a list of present nodes; collecting the identifiers is the job of whoever asked.

The Repeat Message Time decides how robust this is. It is normally a whole number n of Message Cycle Times, so each node sends about n NM PDUs in Repeat Message State; the procedure tolerates n − 1 lost PDUs per node. A Repeat Message Time of 0 means there is no Repeat Message State to speak of, and node detection is not possible.

Try it

Step through node detection on body CAN. At the start the gateway needs the bus, the Door ECU and the Light ECU are awake but in Ready Sleep State. Then switch the Light ECU to passive mode (a configuration in which a node never sends NM PDUs; lesson 17) and run it again.

Things to notice. The bit reaches only nodes that are awake: in Prepare Bus-Sleep Mode or Bus-Sleep Mode an NM PDU is handled as any other NM PDU, without node detection. A passive node is never seen, because it never sends. Leaving Repeat Message State does not keep anyone awake: a node that had released the network goes back to Ready Sleep State and silence.
