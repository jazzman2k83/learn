PN learning and dynamic PNC-to-channel mapping

A PNC gateway normally knows from its configuration which channels each PNC uses. With an optional feature it can ask the ECUs on a bus which PNCs they belong to, and extend that mapping at run time.

Lesson 44 took the PNC-to-channel mapping of the gateway as fixed. This lesson shows how it can be learned: what starts the learning, what each ECU answers, what the gateway does with the answers, and how far the specification has got with it.

Why learn the mapping

The gateway's configuration says, per PNC, which channels reach its members: Comfort on BodyCan and Eth, Lighting on BodyCan. If an ECU variant that is fitted later belongs to a PNC on a channel where the gateway does not expect it, the gateway would not forward that PNC there. Dynamic PNC-to-channel mapping (an optional ComM feature of a PNC gateway: the configured mapping of PNCs to channels is extended at run time from what the ECUs report) lets the gateway find out instead. It works as request and response:

  • The gateway starts PN learning (a learning phase in which every ECU on a channel sends its PNC membership in its NM PDUs) on its channels.
  • Every ECU taking part answers with its PNC membership (the PNCs this ECU belongs to; an SWC can set it at run time with ComM_UpdatePncMembership).
  • The gateway sets a mapping entry for every PNC it receives on a channel.

The learning phase, step by step

The request travels in two bits of the Control Bit Vector: the Repeat Message Request, which brings every node back into Repeat Message State, and the Partial Network Learning Bit (bit 5 of the Control Bit Vector: together with the Repeat Message Request it starts the PNC learning phase; cleared when the sender leaves Repeat Message State). While the learning phase is active, ComM refuses to start another one and to read or change the mapping: ComM_PnLearningRequest (ComM API: starts the PNC learning phase on all channels with dynamic mapping), ComM_UpdatePncMembership, ComM_GetPncToChannelMapping, ComM_UpdatePncToChannelMapping and ComM_ResetPncToChannelMapping then return COMM_E_LEARNING_ACTIVE. The reset brings the learned entries back to the configured default. A PNC that is mapped to a channel for transmission only (lesson 44) cannot be combined with dynamic mapping.

On a gateway, the learning request itself is forwarded like a PNC request, without mirroring it back: from an active channel to all other coordinated channels with dynamic mapping, from a passive channel to the active ones. The membership bits that arrive are forwarded by the same rule, merged into the gateway's own membership.

What is valid in R25-11

PN learning arrived in R20-11 as a draft and is still not finished everywhere. In the R25-11 documents:

PartStatus in R25-11
ComM_PnLearningRequest, ComM_UpdatePncMembership, ComM_Nm_PncLearningBitIndication, ComM_Nm_RepeatMessageLeftIndicationvalid
Nm_PnLearningRequest, CanNm_PnLearningRequestvalid
UdpNm_PnLearningRequest and the UdpNm configuration of the featuredraft: on Ethernet PN learning is not yet standardized
the NmIf configuration switches that enable the featuredraft
the ComM rule that sets a mapping entry from a received ERA bitdraft
the C functions to get, update and reset the mappingvalid; the same operations on the SWC port are marked draft

So the core of the feature, the step from the received bits to the mapping, is still a draft, and in the example ECU learning can be described only for body CAN. Treat it as optional and check what your basic software supplier implements.

4.4.0 has no PN learning and no dynamic mapping. In R20-11 the feature is new: Nm_PnLearningRequest, CanNm_PnLearningRequest, UdpNm_PnLearningRequest, ComM_Nm_PncLearningBitIndication and ComM_Nm_RepeatMessageLeftIndication are drafts there. From R22-11 the ComM, NmIf and CanNm functions are valid; the UdpNm function has stayed a draft up to R25-11.

Things to notice. PN learning reuses what NM already has: the Repeat Message Request brings every node into Repeat Message State, and the PNC bit vector carries the answers. The phase ends by itself when Repeat Message State ends. Only a PNC gateway keeps a mapping; the other ECUs only answer. Much of the feature is still draft in R25-11, on Ethernet all of it.
