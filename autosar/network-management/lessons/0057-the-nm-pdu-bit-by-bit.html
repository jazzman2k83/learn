Network and Mode Management in AUTOSAR Classic

Network Management

The NM PDU bit by bit

Lesson 15 showed the four parts of an NM PDU. This page goes down to the bits: where each part may sit, what each bit of the Control Bit Vector means, and how a bit of the PNC bit vector turns into a PNC number.

The layout is the same for CanNm and UdpNm; the differences are listed at the end. The configuration parameters named here are those of lesson 55.

The system bytes

The system bytes (the bytes of the NM PDU that NM itself uses: the Source Node Identifier and the Control Bit Vector) come first. Each of them is configured to byte 0, byte 1 or off (SWS_CanNm_00074, SWS_CanNm_00075): CanNmPduNidPosition for the Source Node Identifier and CanNmPduCbvPosition for the Control Bit Vector, each with the values CANNM_PDU_BYTE_0, CANNM_PDU_BYTE_1 or CANNM_PDU_OFF. The definitions add three rules (ECUC_CanNm_00026):

  • both may not use the same byte;
  • if the Control Bit Vector is used and the node identifier is off, the Control Bit Vector is in byte 0;
  • with node detection switched on, the Control Bit Vector may not be off.

A part that is off takes no space: its byte is free for user data or the PNC bit vector. CanNm writes CanNmNodeId into the Source Node Identifier byte (SWS_CanNm_00013). After initialization the Control Bit Vector is 0x00 (SWS_CanNm_00085) and every user data byte is 0xFF (SWS_CanNm_00025).

Bits 1 and 2 were used in AUTOSAR R3.2 for an NM coordinator ID; the specification still notes this, and bit 1 has since been reused. With partial networking on, CanNm sends the PNI bit as 1 (SWS_CanNm_00413), and a received NM PDU with PNI 0 is ignored unless CanNmAllNmMessagesKeepAwake is true (SWS_CanNm_00410, SWS_CanNm_00411). The car wakeup bit is not part of the Control Bit Vector: its byte and bit are configured freely with CanNmCarWakeUpBytePosition and CanNmCarWakeUpBitPosition.

The PNC bit vector and the PNC ID

Where the PNC bit vector sits is set in NmIf: NmPncBitVectorOffset (in bytes from the start of the NM PDU) and NmPncBitVectorLength. It lies after the system bytes and within the length of the NM PDU. Each bit stands for one PNC. ComM computes the place of a PNC as (SWS_ComM_00825):

  • byte in the PNC bit vector = (PNC ID div 8) − offset
  • bit = PNC ID mod 8

Counted from the start of the NM PDU, this simply means: PNC ID = byte × 8 + bit. On body CAN, with an offset of 2 and a length of 1, byte 2 holds PNCs 16 to 23. Comfort (16) is bit 0 and Lighting (17) bit 1. A PNC ID below 16 has no place in this layout. In general a ComMPncId lies between 8 and 511 (ECUC_ComM_00874).

The specifications do not write this formula the same way. ComM does not name the offset it subtracts; this course takes it as NmPncBitVectorOffset, the only offset of the PNC bit vector that is configured. The NmIf specification (note to SWS_Nm_00537) and the NM protocol specification write byteIndex = PNC ID div 8 without any offset, for the byte "within the PNC bit vector". Read literally, that would put PNC 16 into byte 2 of the PNC bit vector, which a vector of one byte does not have. Read as the byte of the NM PDU, it gives the same place as ComM's formula. Check how your basic software counts before you assign PNC IDs.

Where the user data may go

Every byte that is neither a system byte nor part of the PNC bit vector is user data (SWS_CanNm_00501). With partial networking, the user data is one block: either between the system bytes and the PNC bit vector (its length is then the offset minus the number of system bytes) or between the end of the PNC bit vector and the end of the NM PDU (its length is the PDU length minus offset minus vector length). Without partial networking, it is the PDU length minus the system bytes. The length of the NM PDU itself is the PduLength of the global PDU in the ECU configuration.

The CanNm specification gives an example of the first case: Control Bit Vector in byte 0, node identifier in byte 1, NmPncBitVectorOffset 4 and NmPncBitVectorLength 4. Bytes 2 and 3 are user data, bytes 4 to 7 the PNC bit vector. The example ECU uses the second case.

UdpNm: the same layout, larger

UdpNm places its system bytes with UdpNmPduNidPosition and UdpNmPduCbvPosition, with the same values (UDPNM_PDU_BYTE_0, UDPNM_PDU_BYTE_1, UDPNM_PDU_OFF) and the same rules (SWS_UdpNm_00074, SWS_UdpNm_00075). Its PNC bit vector is placed by the same two NmIf parameters, and its user data follows the same rules (SWS_UdpNm_00491). The difference is size: an NM packet on Ethernet is not limited to the eight bytes of a classic CAN frame, so its PDU length can leave room for a longer user data block or PNC bit vector. The R25-11 UdpNm specification no longer draws the Control Bit Vector; it names the same bits (Repeat Message Request, PNI, Partial Network Learning, NM Coordinator Sleep Ready, Active Wakeup, PN Shutdown Request), and the last UdpNm specification that draws it (R22-11) shows the same bit positions as CanNm.

In 4.4.0 (and up to R19-11) bits 1 and 5 of the Control Bit Vector were reserved: the PN Shutdown Request Bit and the Partial Network Learning Bit appear in R20-11. Bits 1 and 2 were marked as the R3.2 NM coordinator ID.

Up to R21-11 the place of the PNC bit vector was configured in the bus NM as the PN info range: CanNmPnInfoOffset (1 to 63) and CanNmPnInfoLength in CanNmPnInfo, and the same with UdpNm names. Since R22-11 it is NmPncBitVectorOffset and NmPncBitVectorLength in NmIf.

Things to notice. The PNC ID is simply the bit number counted over the whole NM PDU: byte × 8 + bit. That is why the offset decides the lowest PNC a bus can carry. Bits 2 and 7 of the Control Bit Vector are reserved; bit 1 was reserved too until R20-11.
