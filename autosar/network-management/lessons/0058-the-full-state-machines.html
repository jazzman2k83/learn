Network and Mode Management in AUTOSAR Classic

Network Management

The full ComM and CanSM state machines

Lessons 6 and 21 showed the main paths through the ComM channel state machine and the CanSM network state machine. This page lists every transition of both, with its trigger, condition, effect and the requirement that defines it.

Each state machine exists once per channel or CAN network. In the diagrams, every arrow carries a number; the table below the diagram explains it; its last column gives the requirement numbers. Click a state, or tab to it and press Enter, to see only its transitions.

The ComM channel state machine

Three main states, two of them with two sub-states each (SWS_ComM_00879 to SWS_ComM_00881). After initialization a channel is in COMM_NO_COM_NO_PENDING_REQUEST, without telling the users (SWS_ComM_00485, SWS_ComM_00313). Entering COMM_FULL_COMMUNICATION leads to COMM_FULL_COM_NETWORK_REQUESTED unless a transition names another sub-state (SWS_ComM_00899); entering COMM_NO_COMMUNICATION always leads to COMM_NO_COM_NO_PENDING_REQUEST (SWS_ComM_00898). "Limitation disabled" in the table means that limit to COMM_NO_COMMUNICATION is not active for the channel.

The effects listed for a target state happen on entry, whichever transition leads there. On entering COMM_FULL_COMMUNICATION ComM requests the mode from the bus state manager (SWS_ComM_00069); on entering COMM_SILENT_COMMUNICATION it requests silent communication (SWS_ComM_00071); on entering COMM_NO_COMMUNICATION it requests no communication and, with FULL, calls Nm_NetworkRelease (SWS_ComM_00073, SWS_ComM_00288).

The CanSM network state machine

CanSM runs one state machine, CANSM_BSM, per CAN network (SWS_CanSM_00266 and Figure 7.1 of the CanSM specification). Its transitions are written as trigger, guarding condition (a condition in square brackets that must hold for the transition to be taken) and effect (an action done on the transition). Triggers are named T_…, guarding conditions G_…, effects E_…. All effects run in the CanSM main function (SWS_CanSM_00428). Requests of ComM become triggers: CanSM_RequestComMode with COMM_FULL_COMMUNICATION is T_FULL_COM_MODE_REQUEST, and so on (SWS_CanSM_00425, SWS_CanSM_00499, SWS_CanSM_00426).

The sub state machines of CanSM

Six states of CANSM_BSM are themselves state machines. Each step requests a mode from the CanIf, waits for the indication and repeats the request after CanSMModeRequestRepetitionTime if it times out; after CanSMModeRequestRepetitionMax repetitions CanSM reports CANSM_E_MODE_REQUEST_TIMEOUT (SWS_CanSM_00385). Without a configured transceiver the transceiver steps are skipped (SWS_CanSM_00560).

R25-11 names the callback that CanSM calls ComM_CanSM_ModeIndication (ComM defines it as ComM_<Bus>SM_ModeIndication); up to R24-11 it was ComM_BusSM_ModeIndication, and the R25-11 CanSM specification text still uses that name in its effects.

In 4.4.0 and R20-11 the ComM channel state machine has the same states. In 4.4.0 (up to R19-11) the NM variant for a LIN slave is called LINSLAVE: transitions 11 and 20 exist there with the same requirements, written for LINSLAVE. SLAVE_PASSIVE does not exist yet, so transition 12 applies to PASSIVE only and transition 20 to LINSLAVE only. R20-11 replaces LINSLAVE by SLAVE_ACTIVE and adds SLAVE_PASSIVE.

Things to notice. In ComM, requests and diagnostics move a channel up, NM indications move it down, and the NM variant decides which downward path applies. In CanSM, every way down goes through CANSM_BSM_S_PRE_NOCOM, every way up through CANSM_BSM_S_PRE_FULLCOM, and a bus-off in silent communication is handled in its own state.
