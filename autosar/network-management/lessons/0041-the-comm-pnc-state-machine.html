Network and Mode Management in AUTOSAR Classic

Network Management

The ComM PNC state machine

For every PNC, ComM keeps a small state machine of its own: is the PNC needed here, needed only by other ECUs, about to go, or off? Its state decides whether ComM requests the PNC's channels.

Lesson 40 showed how PNC requests travel in the NM PDU. This lesson follows one PNC, Comfort, through the states of ComM on the gateway, and shows what each state does to the channel.

One state machine per PNC

ComM runs one PNC state machine (the ComM state machine of one PNC: whether it is requested here, kept awake by others, preparing to sleep, or off) per PNC, no matter on how many channels the PNC lives. It has two main states:

  • COMM_PNC_NO_COMMUNICATION (the PNC is off: nobody inside the ECU or outside requests it) is the state after power on.
  • COMM_PNC_FULL_COMMUNICATION (the PNC is active; main state with three sub-states) has the sub-states COMM_PNC_REQUESTED (a ComM user of this ECU requests the PNC), COMM_PNC_READY_SLEEP (no user of this ECU requests it any more, but the PNC is still requested, by other ECUs or by this ECU's last NM PDUs) and COMM_PNC_PREPARE_SLEEP (nobody requests the PNC any more; a timer runs before it is switched off).

ComM reports every change of a PNC state to BswM, whose rules can react, for example by switching the PNC's I-PDU groups.

What moves the state machine

Three kinds of trigger move the state machine:

inside the ECU

ComM users

A user mapped to the PNC calls ComM_RequestComMode with full or no communication. In the example, UserComfort is mapped to Comfort.

from the buses

EIRA bits

NmIf calls ComM_Nm_UpdateEIRA whenever a bit of the EIRA (one bit per PNC: 1 while any ECU, this one included, requests the PNC; lesson 42) changes.

inside ComM

A timer

The PNC prepare sleep timer (the time a PNC stays in COMM_PNC_PREPARE_SLEEP before it is switched off) runs in the last sub-state.

On a PNC gateway (an ECU that forwards PNC requests between channels, lesson 44) a fourth trigger joins in: the ERA (the external requests per channel, one bit per PNC; lesson 42), reported with ComM_Nm_UpdateERA. This lesson leaves the gateway role out. A wakeup can also start a PNC: with ComM_EcuM_PNCWakeUpIndication (EcuM reports a wakeup that belongs to one PNC), or with ComM_EcuM_WakeUpIndication when ComM is configured for a synchronous wakeup, the PNC goes from no communication straight to COMM_PNC_PREPARE_SLEEP. The prepare sleep timer then gives the other ECUs time to send their requests.

    What the PNC state does to the channel

    A PNC has no bus of its own: it lives on the channels it is mapped to, Comfort on BodyCan and Eth in the example. ComM treats a request that comes from a PNC state machine like a user request for those channels, with communication allowed and communication inhibition applying as usual.

    PNC stateIRA bit sent to NmIfChannel request from this PNC
    COMM_PNC_REQUESTED1On entry, ComM requests COMM_FULL_COMMUNICATION for every channel of the PNC, even if it is already requested; it can also be configured to call Nm_NetworkRequest again, so that NM sends its PNC bits at once.
    COMM_PNC_READY_SLEEP0On entry from COMM_PNC_REQUESTED, ComM releases the full communication request of the PNC. The channels stay in COMM_FULL_COMMUNICATION, which holds as long as the PNC is in COMM_PNC_FULL_COMMUNICATION.
    COMM_PNC_PREPARE_SLEEP0No request; the channels still stay in COMM_FULL_COMMUNICATION.
    COMM_PNC_NO_COMMUNICATION0The PNC no longer holds the channels; they follow their own users and NM.

    ComM runs the PNC actions before the channel actions in each main function, so a channel always sees the latest PNC requests.

    The path through NmIf

    In R25-11 the PNC bits travel between ComM and the bus NMs only through NmIf:

    1. When a PNC enters or leaves COMM_PNC_REQUESTED, ComM sets or clears its bit in the IRA (Internal Request Array: the PNC bits this ECU requests on one channel) and passes the IRA of each affected channel with Nm_UpdateIRA.
    2. CanNm or UdpNm fetches the internal requests from NmIf every time it sends an NM PDU and copies them into the PNC bit vector.
    3. NmIf combines the received PNC bits of all channels with the ones this ECU sends. When a bit of the result changes, it calls ComM_Nm_UpdateEIRA. A bit drops back to 0 only when the request has not been repeated for the PNC reset timer (the time after which a PNC request that no NM PDU has repeated counts as gone; lesson 42).

    This is why COMM_PNC_READY_SLEEP follows COMM_PNC_REQUESTED even when no other ECU wants the PNC: this ECU's own last NM PDUs still carry the bit, and the EIRA bit stays 1 until the reset time has passed.

    The state machine itself is the same in 4.4.0 and R20-11. The way the bits travel differs: up to R20-11 the bus NMs computed EIRA and ERA, and ComM read them and sent its own requests through COM signals; NmIf took no part. R21-11 added the NmIf path described here and R22-11 removed the COM path. Lesson 53 shows the older way.

    Things to notice. A local user request wins everywhere. Without a local request, only the EIRA bit decides, and the EIRA bit includes this ECU's own recent requests. The way back to no communication always passes COMM_PNC_PREPARE_SLEEP and its timer. While the PNC is in any sub-state of COMM_PNC_FULL_COMMUNICATION, its channels stay in full communication.
