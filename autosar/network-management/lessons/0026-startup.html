Network Management

Startup: from reset to BswM

The STARTUP phase does as little as possible: a few drivers, the choice of configuration, the OS, the scheduler and BswM. Everything else, the whole communication stack included, starts later under BswM's rules.

Before EcuM: the startup code

After a reset the microcontroller runs its startup code: a stack is set up, the C variables are initialized, and the code can run. EcuM assumes this minimal initialization has happened before the startup code calls EcuM_Init (the first EcuM function after reset: initializes the drivers of the init lists and starts the OS). There is no OS yet and no task.

StartPreOS: inside EcuM_Init

EcuM_Init runs the StartPreOS Sequence (the part of startup in EcuM_Init, before the OS runs). It should be short, and interrupts should not be used in it; if they must, only interrupts that need no OS (category I).

  1. Interrupt priorities (optional callout), on ECUs where they are programmable.
  2. Init block 0: the callout EcuM_AL_DriverInitZero initializes the drivers of driver init list (the configured list of drivers EcuM initializes, in order) zero. These may not use the post-build configuration, because it has not been chosen yet. The recommended content: the Default Error Tracer first, the pre-initialization of DEM, and the drivers needed to read the post-build configuration data.
  3. Selecting the post-build configuration: the callout EcuM_DeterminePbConfiguration returns a pointer to the post-build configuration (the configuration data of EcuM and all other BSW modules that is chosen at startup, not compiled in) to use. EcuM checks that it is consistent with the code; if not, it calls its error hook.
  4. Init block I: EcuM_AL_DriverInitOne initializes driver init list one, now with the post-build configuration: typically MCU, port, timer, watchdog, ADC, ICU and PWM drivers.
  5. Reset reason: EcuM asks the MCU driver why the ECU started and maps the answer to a wakeup source (the source of a wakeup, such as ECUM_WKSOURCE_POWER), which it validates later in UP.
  6. Default shutdown target: EcuM selects the configured default, so that a target exists from the start.
  7. Loop detection (optional callout), then StartOS. EcuM_Init never returns.

StartPostOS: EcuM_StartupTwo

With StartOS, EcuM gives up control. To get it back, the integrator configures an OS task that starts automatically and calls EcuM_StartupTwo (the EcuM function run first in an OS task after the OS has started) as its first action. It runs the StartPostOS Sequence (the part of startup after the OS has started): start the BSW Scheduler (SchM, the BSW Scheduler that calls the main functions and provides the critical sections), initialize BswM, initialize SchM and start the scheduler timing, so the periodic events for BSW and SWCs begin. Then STARTUP is over, and the UP phase begins.

BswM continues

From here on, BswM's action lists do the rest, in the order the integrator configures. One typical action calls an EcuM function generated from a third driver init list, for the BSW initialized by BswM. Others start NvM and read its data; the integrator is responsible for initializing COM, DEM and FIM at the end of that read. Further actions initialize the communication stack (ComM, CanSM, EthSM and the rest) and start the RTE, which starts the SWCs. The specification recommends initializing drivers in UP wherever possible, to keep STARTUP short.

Step through the calls. The grey bands show the execution context: first plain startup code without an OS, then the OS task that calls EcuM_StartupTwo, then BswM.

Things to notice. Init list zero runs before the post-build configuration is known, so it may only contain modules that do not need it. EcuM_Init never returns: EcuM gets control back only through the OS task that calls EcuM_StartupTwo. No communication module is started in STARTUP; ComM, CanSM and EthSM start in UP under BswM.
