Network and Mode Management in AUTOSAR Classic

Network Management

The PNC gateway

The PNC Comfort lives on body CAN and on Ethernet. For a request of the Door ECU to reach the Head unit, the gateway has to turn what it receives on one bus into its own request on the other.

Lesson 42 introduced the ERA, the external requests per channel. This lesson shows what ComM does with it when the ECU is a PNC gateway: which requests it forwards, which it mirrors back, and how several gateways form a hierarchy.

Why the gateway has to forward

Without the gateway function, the body gateway handles Comfort like any other ECU. When the Door ECU requests Comfort, the gateway's EIRA bit becomes 1 and its PNC state machine goes to COMM_PNC_READY_SLEEP. But the gateway puts the Comfort bit into its own NM PDUs only for its own ComM users. On Ethernet nobody sends the Comfort bit, and the Head unit keeps sleeping.

A PNC gateway (an ECU that forwards PNC requests between its channels, so that a PNC can span several buses) solves this. Its configuration states for each PNC which channels reach the members of that PNC, the PNC-to-channel mapping: Comfort on BodyCan and Eth, Lighting on BodyCan. A PNC request received on one channel makes the PNC state machine enter COMM_PNC_REQUESTED, as if a local user had asked, and the gateway sends the bit on the PNC's other channels.

Active and passive channels

Each channel of the gateway gets a gateway type, or none:

COMM_GATEWAY_TYPE_ACTIVE

The gateway coordinates this channel

On an active PNC gateway channel (the gateway coordinates the PNC there: it collects the requests and sends the combined result back) the gateway sends every PNC that is requested anywhere, including a request it received on this same channel. So all ECUs on the channel see the same requests, and the gateway is the last node on the channel to release a PNC.

COMM_GATEWAY_TYPE_PASSIVE

Someone above coordinates

On a passive PNC gateway channel (another, superior coordinator coordinates the channel; the gateway only reports upwards) the gateway sends only its own requests and the requests from its active channels. It never sends back what it received on the passive channel. A channel is passive only where it connects two gateways: one coordinates it actively, the other passively.

no type

Not coordinated

A channel without a gateway type takes no part in forwarding. ERA bits of it are not used by ComM.

Mirroring back only on active channels prevents an endless loop of "phantom" requests: if two gateways both mirrored the same bit to each other, neither could ever release it. The result is a hierarchy for each PNC:

  • The top-level PNC coordinator (a gateway whose channels of this PNC are all active) sees every request of the PNC in the network and sends the result down.
  • An intermediate PNC coordinator (a gateway with a passive channel towards a superior coordinator) aggregates its lower channels, reports up on the passive channel, and passes what comes from above down to its active channels.
  • A PNC leaf node (an ECU that is no PNC coordinator) only requests PNCs and follows the bits it receives.

In the example ECU, BodyCan and Eth both have the type ACTIVE: the body gateway is the top-level coordinator of Comfort and Lighting, and the other ECUs are leaf nodes. Figure 1 shows the other case, where a coordinator above makes Eth passive.

ComM's rules for one PNC on a gateway, where all channels of the PNC have a gateway type, come down to this:

SituationWhat ComM does
a local ComM user requests the PNCCOMM_PNC_REQUESTED; Comfort bit in the IRA of all channels of the PNC, active and passive
ERA bit 1 on an active channelCOMM_PNC_REQUESTED; bit in the IRA of all active channels (mirrored back on the source channel too) and of all passive channels (reported up)
ERA bit 1 on a passive channel onlyCOMM_PNC_REQUESTED; bit in the IRA of the active channels only (passed down, never mirrored up)
no local user, all ERA bits 0COMM_PNC_READY_SLEEP; bit cleared in every IRA; from there as in lesson 41

In COMM_PNC_REQUESTED the PNC requests full communication on all its channels, whatever caused the request. ComM passes each changed IRA to NmIf with Nm_UpdateIRA.

Gateway types

PNCs without a gateway type

A gateway ECU may also have PNCs that it does not coordinate. If none of the channels of a PNC has a gateway type, the PNC behaves as on an ECU without a gateway: only local users put its bit into the IRA, and ERA bits play no part. A PNC on several channels is coordinated either on all of them or on none. If it is not coordinated, the network design has to make sure that its channels are requested and released at the same time, because an application expects all channels of a requested PNC to be in full communication.

Not every PNC has to be handled in both directions. A PNC can be mapped to a channel for transmission only: the gateway then sends the PNC bit there when the PNC is requested, without requesting the channel itself unless a local user asks. And a filter mask that passes a PNC on a channel to which the PNC is not mapped lets the gateway forward requests from that channel without mirroring them back.

More than one top-level coordinator

For different PNCs, different gateways can be the top-level coordinator. One PNC usually has one. It can also have several, but only if the network topology meets a design constraint of the AUTOSAR System Template; a gateway is top-level for a PNC simply when all its channels of that PNC are active. This matters for the synchronized shutdown of lesson 45, which only a top-level coordinator starts.

Managing and managed channels

A ComM channel can manage other channels. The managing channel (a ComM channel with the NM variant FULL that handles NM for the channels it manages) talks to NmIf; each managed channel (a ComM channel without NM of its own, NM variant LIGHT, that follows its managing channel) has exactly one managing channel. A managed channel has no gateway type: PNC coordination happens on the channel with NM.

The gateway rules are the same in 4.4.0 and R20-11, but the bits travel differently: the bus NMs computed the ERA, and ComM read it and sent its requests through COM signals (lesson 53). The behaviour of a PNC whose channels have no gateway type, on an ECU with the gateway enabled, was first specified in R19-11; in 4.4.0 the requirements assume that every channel of a gateway has a type. Transmission-only PNCs and the description of different top-level coordinators for different PNCs came with R21-11; up to R23-11 only one top-level coordinator per PNC is supported, several for the same PNC are allowed from R24-11. Managing and managed channels exist since 4.4.0.

Things to notice. On an active channel the gateway sends back what it received there; on a passive channel it never does. That one rule gives each PNC a tree with a top-level coordinator, intermediate coordinators and leaf nodes. A request from anywhere puts the PNC into COMM_PNC_REQUESTED on the gateway, and with it all its channels into full communication.
