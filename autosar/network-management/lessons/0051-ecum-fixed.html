Network Management

EcuM Fixed

Before EcuM Flex and BswM took over, the ECU State Manager came with one state machine that the standard fixed: it kept the ECU in RUN while anyone asked for it, and it decided by itself when to shut down.

Releases on this page: AUTOSAR 4.0.3 to 4.3.1. EcuM Fixed has its own specification up to 4.3.1, which marks it obsolete; 4.4.0 removes it. R25-11, the release of the rest of this course, has only EcuM Flex (lessons 25 to 32).

Read this page if your project still uses EcuM Fixed. It shows the fixed states, how RUN and POST_RUN requests keep the ECU running, how EcuM Fixed works together with ComM, its callouts, and the TTII protocol. Configuration names appear openly here, because reading an old configuration is part of the topic.

One state machine, fixed by the standard

EcuM Fixed (the older EcuM variant with its own fixed state machine that decides shutdown itself) knows six main states: OFF, STARTUP, RUN, SHUTDOWN, SLEEP and WAKEUP. Most of them have sub-states. The type EcuM_StateType encodes the main state in the high nibble and the sub-state in the low nibble, so ECUM_STATE_APP_RUN = 0x32 belongs to ECUM_STATE_RUN = 0x30. The specification text also uses older names for some of them: RUN II and RUN III for the two RUN sub-states, STARTUP I and II, WAKEUP I and II, GO OFF I and II.

The SWCs see these states through a mode port of EcuM: the RTE switches the mode to STARTUP, RUN, POSTRUN, SHUTDOWN or SLEEP at the points where the state machine passes them.

RUN: who keeps the ECU running

An SWC that needs the ECU calls EcuM_RequestRUN and later EcuM_ReleaseRUN; for clean-up work after that it calls EcuM_RequestPOST_RUN and EcuM_ReleasePOST_RUN. Each EcuM user can place one request of each kind; EcuM Fixed tracks them per user. In EcuM Fixed these requests decide on their own: while one RUN request is placed the ECU stays in RUN, and once the last POST_RUN request is gone it shuts down. No BswM rule is involved.

entering APP_RUN

Allow communication, start the timer

EcuM calls the callout EcuM_OnEnterRun, indicates RUN to the RTE, calls ComM_CommunicationAllowed(channel, TRUE) for every channel of its list and starts a timer: it stays at least EcuMRunMinimumDuration (seconds) in RUN, so that the SWCs have time to place their RUN requests after startup.

leaving APP_RUN

No request, no communication, timer over

In EcuM_MainFunction EcuM checks the RUN requests and the timer, and reads every ComM channel with ComM_GetState. Only when no RUN request is left, the timer has run out and every channel reports COMM_NO_COM_NO_PENDING_REQUEST, it calls ComM_CommunicationAllowed(channel, FALSE), the callout EcuM_OnExitRun, and enters APP_POST_RUN.

in APP_POST_RUN

Back to RUN, or on to SHUTDOWN

A new RUN request sends EcuM straight back to APP_RUN. So does a ComM channel in COMM_NO_COM_REQUEST_PENDING: someone wants to communicate. When no POST_RUN request is left and no RUN request came, EcuM calls EcuM_OnExitPostRun and enters SHUTDOWN.

ComM as a resource manager

EcuM Fixed treats ComM as a resource manager (a BSW module with its own state machine that has one idle state; while it is not idle, it keeps the ECU in RUN). For ComM the idle state is no communication. A ComM user that requests full communication therefore keeps the ECU running without any RUN request of its own: the EcuM Fixed specification calls this an implicit RUN request. The ComM specification of 4.3.1 implements it through ComM_GetState: EcuM Fixed polls every channel and leaves RUN only when all of them are idle. The rule for SWCs follows from it: an SWC that wants to communicate asks ComM, an SWC that needs the ECU without communication asks EcuM.

Because EcuM Fixed calls ComM_CommunicationAllowed itself, a configuration names the channels: EcuMComMCommunicationAllowedList holds references to the ComM channels for which EcuM makes these calls. In R25-11 BswM makes the same call through an action list (lesson 9).

    Shutdown, sleep and wakeup

    In PREP_SHUTDOWN EcuM calls EcuM_OnPrepShutdown and shuts down the DEM. With a sleep mode as shutdown target it continues in GO_SLEEP: EcuM_OnGoSleep, the NvM write-all job, and EcuM_EnableWakeupSources for every wakeup source of that sleep mode; the OS keeps running. With OFF or RESET it continues in GO_OFF_ONE: EcuM_OnGoOffOne, the RTE is stopped, ComM is de-initialized and the OS is shut down; GO_OFF_TWO then calls EcuM_OnGoOffTwo and switches off through the callout EcuM_AL_SwitchOff, or resets through the MCU driver. EcuM Fixed never puts the ECU into SLEEP while a RUN request is still placed.

    A wakeup leads through the WAKEUP sub-states. WAKEUP_ONE restores the normal MCU mode, disables the pending wakeup source and restarts the drivers (EcuM_AL_DriverRestart). WAKEUP_VALIDATION runs the same wakeup validation as EcuM Flex (lesson 34): EcuM_StartWakeupSources, EcuM_CheckValidation until a source is validated or its validation timeout runs out. On success EcuM calls ComM_EcuM_WakeUpIndication for the channel of the source, and ComM moves that channel to COMM_NO_COM_REQUEST_PENDING. WAKEUP_REACTION chooses one of three reactions: ECUM_WKACT_RUN (on through WAKEUP_TWO to RUN), ECUM_WKACT_TTII, or ECUM_WKACT_SHUTDOWN, which is also the default when nothing was validated. The callout EcuM_OnWakeupReaction may override the choice.

    TTII: sleeping deeper over time

    TTII (time triggered increased inoperation: a timer wakes the ECU again and again, and after a configured number of these wakeups EcuM selects the next, deeper sleep mode) exists only in EcuM Fixed. Each entry of the list names a sleep mode, its successor and a divisor: how often the ECU must be woken up before the successor is selected. When the configured TTII wakeup source is the only wakeup, WAKEUP_REACTION chooses ECUM_WKACT_TTII: EcuM counts the divisor down and, at the end, switches to the successor sleep mode. Every time RUN is reached, TTII starts again from its first entry. Configuration: EcuMTTIIEnabled and EcuMTTIIWakeupSourceRef in EcuMFixedGeneral, one EcuMTTII container (EcuMDivisor, EcuMSleepModeRef, EcuMSuccessorRef) per list entry. EcuM Flex has no TTII; its alarm clock (lesson 31) covers timed wakeups.

    The configuration, briefly

    An EcuM Fixed configuration is easy to recognise: it has the containers EcuMFixedGeneral and EcuMConfiguration/EcuMFixedConfiguration, all marked obsolete in 4.3.1. EcuMFixedConfiguration holds EcuMRunMinimumDuration, EcuMComMCommunicationAllowedList, the NvM timeouts EcuMNvramReadallTimeout and EcuMNvramWriteallTimeout, EcuMNormalMcuModeRef, the init lists EcuMDriverInitListTwo and EcuMDriverInitListThree, the users (EcuMFixedUserConfig with EcuMFixedUser, for SWCs and for modules below the RTE such as ComM) and the TTII list. EcuMFixedGeneral adds EcuMIncludeComM and the TTII switches. The wakeup sources (EcuMWakeupSource with EcuMComMChannelRef and EcuMValidationTimeout) and the sleep modes live in the common part, as in EcuM Flex.

    In 4.0.3, EcuM_KillAllPostRUNRequests does not exist yet; 4.1.2 added it next to EcuM_KillAllRUNRequests, which clears every RUN request and leads into a controlled shutdown. The 4.0.3 specification also names the generated symbol of EcuMRunMinimumDuration ECUM_RUN_SELF_REQUEST_PERIOD. The states and their values are the same from 4.0.3 to 4.3.1.

    Things to notice. In EcuM Fixed the RUN requests themselves decide: no request, no ComM channel out of no communication and the minimum duration over means shutdown. EcuM Fixed, not BswM, calls ComM_CommunicationAllowed, and it reads the ComM channels with ComM_GetState. POST_RUN is a real state: a ComM request that arrives there is held as pending and brings the ECU back into RUN.
