Network and Mode Management in AUTOSAR Classic

Network Management

FlexRay and LIN

The course uses CAN and Ethernet. FlexRay and LIN fit into the same picture: ComM sees a channel and a bus state manager, whatever the bus. What changes is the module below ComM, and whether there is network management at all.

The same picture

For every channel, ComM calls <Bus>SM_RequestComMode of the channel's bus state manager, whose prefix is CanSM, EthSM, FrSM or LinSM (by the bus type COMM_BUS_TYPE_CAN, _ETH, _FR or _LIN), and waits for its mode indication. Each bus state manager also reports its state to BswM (BswM_FrSM_CurrentState, BswM_LinSM_CurrentState). The channel state machine of ComM is the same for all four; the NM variant of the channel (8) decides how it goes to sleep.

FlexRay: FrSM and FrNm

FlexRay is time-triggered: all nodes run one shared communication cycle. Starting it is far more involved than on CAN: on CAN any message can wake the bus, on FlexRay a special wakeup pattern is needed. FrSM maps ComM's modes to the states of the FlexRay controllers (FRSM_READY, FRSM_WAKEUP, FRSM_STARTUP, FRSM_ONLINE …) and, if the cluster is configured for it (FrSMIsWakeupEcu), sends the wakeup pattern.

FrNm runs the same coordination algorithm (12) with the same three states inside Network Mode as CanNm, and a Synchronize Mode between Bus-Sleep Mode and Network Mode. Instead of one NM PDU it sends NM data and a separate NM-Vote: a node that needs the bus votes to keep it awake. When no node has voted for (FrNmReadySleepCnt + 1) repetition cycles, all nodes enter Bus-Sleep Mode at the end of the same cycle. FrNm has no Prepare Bus-Sleep Mode and no Wait Bus-Sleep Time. Because the bus is cyclic, a FlexRay channel is the natural synchronizing network of an NM coordinator (38): FrNm calls Nm_SynchronizationPoint at the points where a coordinated shutdown may start.

LIN: LinSM, no NM

LIN has a master and slaves, and no AUTOSAR network management: NmIf is not involved. LinSM knows only two states per network, LINSM_NO_COM and LINSM_FULL_COM; COMM_SILENT_COMMUNICATION is not used.

  • LIN master. When ComM requests COMM_NO_COMMUNICATION, LinSM has the goto-sleep command sent (LinIf_GotoSleep); the slaves follow. A request for full communication sends a wakeup (LinIf_Wakeup). The master's own channel uses an NM variant without NM; the specifications do not name one for a LIN master.
  • LIN slave, NM variant SLAVE_ACTIVE. The slave cannot keep the bus awake, but it can wake it: a request for full communication makes LinSM send a wakeup signal, and the master starts the bus. The slave sleeps when it receives the goto-sleep command or sees the bus idle; LinSM then tells ComM with ComM_LinSM_BusSleepMode, and ComM goes to COMM_NO_COMMUNICATION.

The LinSM specification of R25-11 writes the sleep notification ComM_BusSM_BusSleepMode and the mode indication ComM_BusSM_ModeIndication; the ComM specification writes them ComM_<Bus>SM_BusSleepMode and ComM_<Bus>SM_ModeIndication. They are the same functions.

Things to notice. ComM, BswM and EcuM work the same on every bus. The bus state manager hides how a bus is switched on and off; the NM variant says who decides that the bus may sleep: the bus NM on CAN, Ethernet and FlexRay, the LIN master on LIN. SLAVE_PASSIVE belongs to Ethernet, not to LIN.
