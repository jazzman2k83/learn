Network and Mode Management in AUTOSAR Classic

Network Management

Troubleshooting

Something in network management or mode management does not behave as expected. Find what you see, go through the causes from the most likely one down, and check the parameters named for each. The second part shows how to read a configuration you did not write, including one from an older release.

Before you start. Record three things at the same time: a bus trace of the NM PDUs, the states of ComM, CanNm and CanSM for the channel, and what BswM receives (the wakeup states from EcuM, the bus state manager states). In the NM PDU of the example gateway, byte 0 is the Source Node Identifier (gateway 0x10, Door ECU 0x21, Light ECU 0x22), byte 1 the Control Bit Vector (bit 0 Repeat Message Request, bit 4 Active Wakeup Bit, bit 6 PNI) and byte 2 the PNC bit vector (bit 0 Comfort, bit 1 Lighting). All times in these configurations are in seconds.

The configuration pages of this course: the configuration map of ComM and NM, the configuration map of CanSM, EthSM and EcuM, the configuration help and the recipes.

Find the cause

Pick what you see, then answer up to three questions about what the trace and the module states show. The answer points to the cause to check first; the sections below list all of them.

Choose a symptom.

The bus never sleeps

All ComM users of the body gateway have released body CAN, but the bus stays awake.

What you see

  • NM PDUs keep coming on body CAN. Their Source Node Identifier tells you which node sends.
  • The ComM channel BodyCan is in COMM_FULL_COM_NETWORK_REQUESTED (this ECU still requests it) or in COMM_FULL_COM_READY_SLEEP (ComM has released it and waits for NM).
  • CanNm of the gateway is in the Ready Sleep State, and every received NM PDU restarts the NM-Timeout Timer, so the Prepare Bus-Sleep Mode never comes.
  1. Another node still keeps the bus awake.

    A node that is in Network Mode (Repeat Message or Normal Operation) sends NM PDUs; every other node in Ready Sleep State stays awake as long as it receives them. This is correct behaviour on the gateway.

    ConfirmThe NM PDUs come from 0x21 or 0x22, and the gateway's CanNm is in Ready Sleep State.

    FixOn that node: find its open request with these same checks. Lesson 13, lesson 14.

  2. A ComM user of this ECU still requests the channel or one of its PNCs.

    UserChassis requests a channel, UserComfort and UserLighting request a PNC; a PNC in COMM_PNC_REQUESTED keeps all its channels requested.

    ConfirmNM PDUs with 0x10 in byte 0; the channel is in COMM_FULL_COM_NETWORK_REQUESTED. With ComMFullCommRequestNotificationEnabled the port ComM_CurrentChannelRequest lists the users that request the channel.

    FixThe SWC must release with ComM_RequestComMode(…, COMM_NO_COMMUNICATION). For a PNC that stays requested see a PNC stays requested. Lesson 5, lesson 41.

  3. Dcm still indicates active diagnostics.

    Dcm calls ComM_DCM_ActiveDiagnostic while a diagnostic request is processed or a session other than the default session is active; ComM treats it like a request for COMM_FULL_COMMUNICATION. A tester that keeps the session alive keeps the channel awake. Dcm goes back to the default session after the S3Server timeout and then calls ComM_DCM_InactiveDiagnostic (SWS_Dcm_01373 to 01377).

    ConfirmNo user requests the channel, but it stays in COMM_FULL_COM_NETWORK_REQUESTED; the Dcm session is not the default session.

    FixEnd the session, or check that DcmDslProtocolComMChannelRef names the channel the tester really uses. Lesson 10.

  4. Repeat Message Requests again and again.

    With CanNmNodeDetectionEnabled, a received Repeat Message Request sends every node from Normal Operation or Ready Sleep State back into the Repeat Message State for CanNmRepeatMessageTime, and each node sends NM PDUs there (SWS_CanNm_00119, 00111). A node that calls Nm_RepeatMessageRequest repeatedly keeps the whole cluster awake. With CanNmPnHandleMultipleNetworkRequests, every change of a requested PNC also re-enters the Repeat Message State.

    ConfirmNM PDUs with bit 0 of the Control Bit Vector set appear again and again; their Source Node Identifier names the requester.

    FixFind what calls the request on that node, or the PNC request that toggles. Lesson 16.

  5. Partial networking lets every NM PDU keep the ECU awake.

    With CanNmPnEnabled, an NM PDU counts only when it carries a PNC that passes the PNC filter mask (SWS_CanNm_00503). Three things switch this off: CanNmAllNmMessagesKeepAwake = TRUE (every NM PDU counts; meant for gateways), a PN availability that was never confirmed (until CanNm_ConfirmPnAvailability is called, all PNC requests count as relevant), and filter mask bytes that pass PNCs this ECU is not a member of.

    ConfirmThe NM PDUs that keep coming carry only PNC bits of other PNCs; the gateway still restarts its NM-Timeout Timer on them.

    FixFilter mask bits only for the PNCs of this ECU; CanNmAllNmMessagesKeepAwake only on a gateway that must stay awake for all of them; check CanSMPncSupport and the transceiver if the confirmation is missing. Lesson 42, lesson 43.

  6. The NM variant is NONE.

    A channel with ComMNmVariant = NONE has no NM; once requested it stays in full communication until the ECU is switched off.

    ConfirmNo NM PDU on the bus at all; the channel sits in COMM_FULL_COM_READY_SLEEP.

    FixFULL on a bus with NM, LIGHT on a bus without NM that must shut down. Lesson 8.

Parameters to look at

The ECU does not wake up

The Door ECU wakes body CAN, but the body gateway stays asleep, or it wakes up and its body CAN channel stays down.

What you see

  • Frames on body CAN, but no EcuM_SetWakeupEvent for ECUM_WKSOURCE_BODYCAN: BswM gets no BswM_EcuM_CurrentWakeup for it.
  • Or the wakeup event is validated, but the channel BodyCan stays in COMM_NO_COM_NO_PENDING_REQUEST or COMM_NO_COM_REQUEST_PENDING.
  1. The wakeup source is not enabled in the sleep mode.

    In the GoSleep sequence EcuM enables only the sources in EcuMWakeupSourceMask of the sleep mode it uses (EcuM_EnableWakeupSources).

    ConfirmThe mask of the selected EcuMSleepMode lacks ECUM_WKSOURCE_BODYCAN; the ECU still wakes on ECUM_WKSOURCE_DOOR_PIN.

    FixAdd the source to the mask. Lesson 30.

  2. The transceiver is not set up to report a bus wakeup.

    The CanTrcv needs CanTrcvWakeupByBusUsed = TRUE and CanTrcvWakeUpSupport other than CANTRCV_WAKEUP_NOT_SUPPORTED;CanTrcvWakeupSourceRef names the EcuM source it reports; CanIf needs CanIfTrcvWakeupSupport. With polling, the sleep mode must be POLL and the source EcuMWakeupSourcePolling.

    ConfirmThe transceiver's wake flag is set but no wakeup event follows, or CanTrcv_CheckWakeup is never called.

    FixComplete the chain transceiver → CanIf → EcuM. Lesson 35.

  3. Selective wakeup filters the frame out.

    With CanTrcvPnEnabled = TRUE the transceiver wakes only on a wakeup frame that matches CanTrcvPnFrameCanId under CanTrcvPnFrameCanIdMask and whose payload has a 1 in a bit of the data mask. The gateway is a member of Comfort and Lighting: with the NM PDU as wakeup frame its data mask on byte 2 is 0x03.

    ConfirmCompare the identifier and byte 2 of the waking NM PDU with the pattern. An NM PDU for a PNC outside the mask must not wake the ECU; that is correct.

    FixSet the data mask bits for exactly the PNCs of this ECU. Lesson 43.

  4. The wakeup is detected but not validated.

    See the wakeup expires.

  5. The wakeup source names no ComM channel.

    EcuM_ValidateWakeupEvent calls ComM_EcuM_WakeUpIndication only for the channels in EcuMComMChannelRef of the source (SWS_EcuM_02645). Without it the ECU runs, but body CAN is never started, and BswM sends the ECU back to sleep.

    ConfirmECUM_WKSTATUS_VALIDATED for ECUM_WKSOURCE_BODYCAN, but the channel stays in COMM_NO_COM_NO_PENDING_REQUEST.

    FixReference BodyCan (and EcuMComMPNCRef for PNCs that the source should wake). Lesson 34, lesson 48.

  6. The channel waits for communication allowed.

    See a request stays pending.

  7. This ECU should wake the bus itself, but a request is refused.

    With wake up inhibition (ComMNoWakeup) a user request for a channel in no or silent communication is inhibited (SWS_ComM_00218); with limit to COMM_NO_COMMUNICATION (ComMNoCom) it is refused too. A wakeup from the bus is still handled. The request returns COMM_E_MODE_LIMITATION.

    FixCheck the inhibition state, the values stored in NvM and ComMEcuGroupClassification. Lesson 11.

Parameters to look at

The wakeup expires

EcuM detects the wakeup of body CAN, but the wakeup validation fails and the ECU goes back to sleep.

What you see

  • BswM gets BswM_EcuM_CurrentWakeup(ECUM_WKSOURCE_BODYCAN, ECUM_WKSTATUS_PENDING) and, after EcuMValidationTimeout, the same with ECUM_WKSTATUS_EXPIRED (SWS_EcuM_04082).
  • During the validation, CanSM of BodyCan should be in CANSM_BSM_WUVALIDATION.
  1. Only NM PDUs validate, but the waking node sends application frames first.

    With CanIfPublicWakeupCheckValidByNM = TRUE, CanIf records only the first received NM PDU for validation; with FALSE, any configured received PDU counts (SWS_CANIF_00286).

    ConfirmThe trace in the validation window shows application frames, but no NM PDU before the timeout.

    FixSet FALSE, or make the waking node send its NM PDUs early. Lesson 35.

  2. The validation timeout is shorter than the time to the first frame.

    The waking ECU needs its own startup time, and in the Repeat Message State the first NM PDU waits for CanNmMsgCycleOffset unless immediate transmissions are used. The CanNm specification notes that the transmission offset can delay the first NM PDU significantly.

    ConfirmMeasure from the wakeup (transceiver wake flag, ECUM_WKSTATUS_PENDING) to the first NM PDU and compare with EcuMValidationTimeout.

    FixA longer timeout on this ECU, or an earlier first NM PDU on the waking one. Lesson 34, lesson 14.

  3. The CAN controller is not started for the validation.

    The callout EcuM_StartWakeupSources must call CanSM_StartWakeupSource; only then are transceiver and controller running and CanIf_RxIndication can be called at all.

    ConfirmCanSM never enters CANSM_BSM_WUVALIDATION.

    FixComplete the callout (integrator code). Lesson 35.

  4. Nobody asks CanIf.

    CanIfPublicWakeupCheckValidSupport must be TRUE, otherwise CanIf records nothing for validation, and the callout EcuM_CheckValidation must call CanIf_CheckValidation for the source.

    ConfirmNM PDUs arrive in time, CanSM is in CANSM_BSM_WUVALIDATION, but the source never becomes validated.

    FixSwitch the support on and complete the callout. Lesson 34.

  5. The wakeup was not a real one.

    A disturbance on the bus or the wake line wakes the transceiver, but no ECU talks. Then EXPIRED is the intended result: validation exists to filter such wakeups.

Parameters to look at

A request stays pending

A user requests body CAN, or the bus wakes the gateway, but the channel never reaches full communication.

What you see

  • The ComM channel stays in COMM_NO_COM_REQUEST_PENDING; ComM does not call CanSM_RequestComMode; the bus stays silent.
  • Or ComM has requested COMM_FULL_COMMUNICATION, but CanSM does not reach CANSM_BSM_S_FULLCOM.
  1. Communication allowed is never set.

    ComM leaves COMM_NO_COM_REQUEST_PENDING only when its flag communication allowed is TRUE (SWS_ComM_00895). In EcuM Flex, BswM sets it through an action BswMComMAllowCom that calls ComM_CommunicationAllowed. If the rule's condition never becomes true (an EcuM state that is not reached, a mode request port that never reports), the request waits forever.

    ConfirmTrace the BswM rule: does its expression become true, and does its action list run?

    FixA rule whose condition is reached after startup and after a wakeup. Lesson 9, lesson 27.

  2. The action names another channel.

    BswMComMAllowChannelRef points to ChassisCan instead of BodyCan, or one action exists for two channels where two are needed.

    FixOne allow action per channel. Lesson 9.

  3. The bus state manager does not reach full communication.

    CanSM repeats an unconfirmed request to CanIf CanSMModeRequestRepetitionMax times, CanSMModeRequestRepetitionTime apart, and then reports CANSM_E_MODE_REQUEST_TIMEOUT (SWS_CanSM_00385). The cause is then in the controller or transceiver configuration below CanSM.

    ConfirmThe error is reported; CanSM stays in CANSM_BSM_S_PRE_FULLCOM.

    FixCheck CanSMControllerId and CanSMTransceiverId against CanIf. Lesson 21.

Parameters to look at

A PNC stays requested

No user needs Comfort any more, but the PNC does not reach COMM_PNC_NO_COMMUNICATION, and with it body CAN stays awake.

What you see

  • The PNC state machine of Comfort is in COMM_PNC_REQUESTED (a local user or, on the gateway, an ERA bit) or in COMM_PNC_READY_SLEEP (an EIRA bit: someone on the bus requests it).
  • NM PDUs on body CAN with byte 2 bit 0 set; their Source Node Identifier tells you who sends the bit.
  1. Another ECU still requests the PNC.

    The Door ECU (0x21) or, through Ethernet, the Head unit still sends the Comfort bit. While an ERA bit of Comfort is 1, the gateway keeps the PNC in COMM_PNC_REQUESTED (SWS_ComM_01084).

    ConfirmNM PDUs with the bit from a node other than 0x10; on the gateway ComM_Nm_UpdateERA reports the bit for that channel.

    FixOn that ECU. Lesson 42.

  2. A local user still requests it.

    UserComfort is mapped to Comfort through ComMUserPerPnc; its request holds the PNC in COMM_PNC_REQUESTED.

    FixRelease the user. Lesson 41.

  3. Two gateways mirror the bit to each other.

    On a channel with COMM_GATEWAY_TYPE_ACTIVE the gateway sends every requested PNC back, including what it received on that channel (SWS_ComM_01072). If two gateways on one channel both have the type ACTIVE, each sees the other's bit in its ERA, and neither can release it.

    ConfirmAfter every leaf node has released, the bit still comes from both gateways' Source Node Identifiers.

    FixOn a channel between two gateways, one coordinates it actively and the other has COMM_GATEWAY_TYPE_PASSIVE. Lesson 44.

  4. The timers are still running.

    A PNC bit stays in EIRA and ERA for NmPnResetTime after the last NM PDU that carried it (SWS_Nm_00319, 00325); its value must be greater than the Message Cycle Time. After that the PNC spends ComMPncPrepareSleepTimer in COMM_PNC_PREPARE_SLEEP. A large value of either looks like a PNC that does not go.

    ConfirmTime from the last NM PDU with the bit to COMM_PNC_NO_COMMUNICATION; it equals the sum of the two times plus main function delays.

    FixValues from the network design, the same for every ECU of the PNC. Lesson 42, lesson 41.

Parameters to look at

Bus-off loops

Body CAN goes bus-off, recovers and goes bus-off again, without end.

What you see

  • On each bus-off CanSM reports CANSM_BSWM_BUS_OFF to BswM, COMM_SILENT_COMMUNICATION to ComM and the DEM event CANSM_E_BUS_OFF as pre-failed; after each recovery BswM and ComM get full communication back (SWS_CanSM_00508, 00521, 00522, 00517, 00518).
  • CanNm reports CANNM_E_NETWORK_TIMEOUT: its NM-Timeout Timer ran out in the Repeat Message or Normal Operation State, for example because of the bus-off.
  1. A fault on the bus.

    A wrong bit rate, missing termination, a short or a faulty node. No configuration of these modules repairs it; bus-off recovery only limits the damage.

    ConfirmA bus analyser shows error frames, also from other nodes.

  2. The recovery never reaches the long time.

    CanSM waits CanSMBorTimeL1 before switching transmission on again, and CanSMBorTimeL2 once CanSMBorCounterL1ToL2 bus-offs have come without a passed recovery check. The check passes CanSMBorTimeTxEnsured after transmission is on again (or, with CanSMBorTxConfirmationPolling, when CanIf reports a transmit confirmation on all controllers), and that resets the count (SWS_CanSM_00514, 00515, 00496, 00497). If the check passes before the next bus-off comes, CanSM retries at the short time forever.

    ConfirmEvery retry uses the level 1 time, even after many bus-offs; DEM gets passed between them.

    FixCanSMBorTimeTxEnsured longer than the time a bus-off needs to come back; a moderate counter; a long level 2 time. Lesson 22.

  3. A bus-off delay callout shortens the waits.

    With CanSMEnableBusOffDelay, the callout named in CanSMGetBusOffDelayFunction supplies the delay instead of the configured times (SWS_CanSM_00636).

    FixCheck what the callout returns. Lesson 22.

Parameters to look at

The channel goes down too early

Body CAN or chassis CAN leaves full communication while other ECUs still communicate, or while this ECU still expects to.

What you see

  • ComM reports COMM_SILENT_COMMUNICATION or COMM_NO_COMMUNICATION for the channel; NmIf calls Nm_PrepareBusSleepMode.
  • Sometimes it comes straight back: an NM PDU received in Prepare Bus-Sleep Mode returns CanNm to the Network Mode (SWS_CanNm_00124).
  1. The NM variant is LIGHT.

    A LIGHT channel stays ComMTMinFullComModeDuration in network requested and then ComMNmLightTimeout in ready sleep, and goes to no communication without asking any other ECU.

    FixFULL on a bus with NM, or timeouts that fit the other ECUs. Lesson 8.

  2. The ECU is passive.

    With PASSIVE, or NmPassiveModeEnabled on the NM channel, the ECU sends no NM PDUs and cannot keep the bus awake; it goes down as soon as the others release.

    ConfirmNo NM PDU with this ECU's Source Node Identifier.

    FixFULL with a transmitted NM PDU (CanNmTxPdu) if the ECU must keep the bus awake. Lesson 17.

  3. The NM-Timeout Time is too short for the cluster.

    In Ready Sleep State only the NM PDUs of the others restart the NM-Timeout Timer. If CanNmTimeoutTime is not longer than the CanNmMsgCycleTime of the other nodes, the timer runs out between two of their NM PDUs.

    ConfirmComM toggles between silent and full communication while the others keep sending.

    FixThe cluster's values for the NM-Timeout Time and Message Cycle Time. Lesson 14.

  4. A mode limitation is active.

    A BswM action BswMComMModeLimitation or a call of ComM_LimitChannelToNoComMode limits the channel: ComM leaves network requested at once (SWS_ComM_00890), and user requests return COMM_E_MODE_LIMITATION. With ComMNoCom = TRUE the limitation is active from initialization.

    FixCheck the inhibition state and the BswM rule. Lesson 11.

  5. The request ended earlier than expected.

    A user released, or Dcm returned to the default session after the S3Server timeout and called ComM_DCM_InactiveDiagnostic. A bus-off also takes the channel to silent communication for a while: see bus-off loops.

    FixFollow the requests over time. Lesson 7, lesson 10.

Parameters to look at

The gateway does not forward a PNC

The Door ECU requests Comfort on body CAN, but the Head unit on Ethernet never sees the bit.

What you see

  • The Comfort bit arrives on body CAN, but the gateway's NM packets on Ethernet do not carry it.
  1. The PNC has no gateway type on its channels.

    ComM uses the ERA only when ComMPncGatewayEnabled is TRUE and the channels of the PNC have a ComMPncGatewayType (SWS_ComM_01066). A PNC without one is handled like on an ECU without gateway.

    FixBoth channels COMM_GATEWAY_TYPE_ACTIVE on the example gateway. Lesson 44.

  2. The filter mask blocks the bit on the receiving channel.

    NmIf stores a received PNC request only if its bit is 1 in the filter mask (SWS_Nm_00323).

    ConfirmComM_Nm_UpdateERA for BodyCan never shows the bit.

    FixNmPnFilterMaskByte with index 0 (the first byte of the PNC bit vector, byte 2 of the NM PDU) and value 0x03. Lesson 42.

  3. No ERA is computed for the channel.

    NmPnEraCalcEnabled must be TRUE on the receiving NM channel, with NmPnEnabled and partial networking in the bus NM (CanNmPnEnabled).

    FixSwitch them on. Lesson 42.

  4. The PNC is not mapped to the other channel.

    ComM puts the bit into the IRA of channels in ComMChannelPerPnc or ComMChannelPerTxOnlyPnc only, and passes it with Nm_UpdateIRA.

    FixMap Comfort to Eth. Lesson 44.

Reading a configuration you did not write

A configuration made by a tool from the network description is easiest to read from the network down. Go through it in this order; each step answers one question, and the later steps depend on the earlier ones.

1Channels and NM variants
→
2Users and PNCs
→
3NmIf and CanNm
→
4Bus state managers
→
5EcuM wakeup sources
→
6BswM rules
  1. Channels and NM variants: which buses, and who decides when each sleeps.

    One ComMChannel per network: ComMChannelId (the network handle), ComMBusType, and in ComMNetworkManagement the ComMNmVariant. Only FULL channels can keep the bus awake; PASSIVE ones follow the others; LIGHT ones go down by timer; NONE ones never. Then check the other side: every FULL and PASSIVE channel needs an NmChannelConfig and a CanNmChannelConfig or UdpNmChannelConfig that reference the same ComM channel (NmComMChannelRef, CanNmComMNetworkHandleRef). Note ComMNoCom and ComMNoWakeup: a TRUE here is an inhibition from the start.

  2. Users and PNCs: who can request what.

    The ComMUsers, the channels they request (ComMUserPerChannel) and the ComMPncs with their ComMPncId, channels (ComMChannelPerPnc) and users (ComMUserPerPnc). A PNC ID must fit the PNC bit vector of its channels: PNC ID = byte × 8 + bit, counted from the start of the NM PDU. For diagnostics, DcmDslProtocolComMChannelRef tells you which channel Dcm keeps awake.

  3. NmIf and CanNm: the timing of the cluster and the partial networking settings.

    In NmGlobalProperties: NmPncBitVectorOffset, NmPnResetTime, NmPnEiraCalcEnabled. Per NmChannelConfig: NmPnEnabled, NmPncBitVectorLength, NmPnEraCalcEnabled, the NmPnFilterMaskBytes, and the coordination settings. Per CanNmChannelConfig: the four timers, CanNmMsgCycleOffset, the immediate transmissions, CanNmNodeId with CanNmPduNidPosition and CanNmPduCbvPosition, node detection and CanNmAllNmMessagesKeepAwake. Compare the timers with the other ECUs of the cluster: they come from the same network description.

  4. Bus state managers: which hardware belongs to a channel, and how it recovers.

    Per CanSMManagerNetwork: CanSMComMNetworkHandleRef, the controllers, CanSMTransceiverId and the bus-off times; CanSMPncSupport for partial networking. Per EthSMNetwork: the EthIf controller. For selective wakeup, the CanTrcvPartialNetwork container of the transceiver.

  5. EcuM wakeup sources: what wakes the ECU, and what it starts.

    Each EcuMWakeupSource in EcuMCommonConfiguration: its bit (EcuMWakeupSourceId), EcuMValidationTimeout (absent: no validation), EcuMComMChannelRef and EcuMComMPNCRef. Then which sleep modes enable it (EcuMWakeupSourceMask) and how CanIf validates (CanIfPublicWakeupCheckValidSupport, CanIfPublicWakeupCheckValidByNM).

  6. BswM rules: when communication is allowed and when the ECU goes down.

    Read each BswMRule with the mode request ports its expression uses (BswMComMIndication, BswMEcuMWakeupSource, BswMCanSMIndication …) and the actions of its action lists: BswMComMAllowCom, BswMComMModeLimitation, BswMEcuMGoDownHaltPoll, and BswMUserCallout for integrator code. Most problems of a waking or sleeping ECU that are not in steps 1 to 5 are here.

A configuration from an older release

A configuration written for 4.4.0 or R20-11 handles partial networking differently: the bus NMs compute EIRA and ERA and pass them as PDUs through PduR to COM, and ComM reads them as COM signals (ComM_COMCbk_<sn>, Com_ReceiveSignal) and writes its own requests with Com_SendSignal. You recognise it by the containers below. A configuration with EcuMFixedGeneral or EcuMFixedConfiguration is older still: EcuM Fixed, 4.3.1 and older.

What survives a move from the COM signal path: the PNC IDs, the offset and length of the PNC bit vector, the filter mask bytes and the reset time keep their values and only change their container. ComMPncGatewayEnabled, ComMPncGatewayType, ComMChannelPerPnc and ComMUserPerPnc keep their names. All other differences between the releases, parameter by parameter, are in release differences and the older and the newer way.
