Network and Mode Management in AUTOSAR Classic

Network Management

Recipe book

Typical configuration jobs for ComM, NmIf, CanNm, UdpNm, CanSM, EthSM, EcuM, CanIf, CanTrcv and Dcm, each as a short list of steps with the parameters to set, the rules to check and the usual mistakes.

How to read a recipe. Each step names the configuration container and the configuration parameter entries to set. The tables give each parameter with the path of its container below it, its multiplicity, what to set and the lesson that explains it. The values are those of the example gateway of lesson 3: channels BodyCan = 0, ChassisCan = 1, Eth = 2, PNCs Comfort = 16 and Lighting = 17. Values marked "e.g." are not fixed by the example and only have to satisfy the rules shown. All times are in seconds. Rule IDs such as ECUC_Nm_00252 and SWS_ComM_00825 point to chapter 10 and chapter 7 of the R25-11 specification of the module.

See also the configuration help overview, the troubleshooting guide, the timer sheet and the configuration maps of lesson 55 and lesson 56.

1. Add a CAN channel with network management

ComM · NmIf · CanNm · CanSM · CanIf · EcuM

Goal. A new CAN bus that wakes up, stays awake while someone needs it and goes to bus sleep together with the other ECUs, under AUTOSAR network management. The example is BodyCan; ChassisCan follows the same steps.

Steps

  1. ComM: the channel. One ComMChannel per bus. Its ComMChannelId is the network handle that ComM, NmIf, CanSM and Dcm use in their calls. Users that need the whole bus go into ComMUserPerChannel; on BodyCan there is none, because its users are mapped to PNCs (recipe 2).

  2. NmIf: the NM channel. One NmChannelConfig per bus with network management, pointing to the ComM channel and naming its bus NM.

  3. CanNm: the bus NM channel. One CanNmChannelConfig with the node identifier, the positions of the Source Node Identifier and the Control Bit Vector, the timers and the NM PDU references. Timer values: see recipe 8.

  4. CanSM and CanIf: the network and its hardware. One CanSMManagerNetwork with the CAN controller and the transceiver, as CanIf knows them. CanIf gets the NM PDUs as L-PDUs that reference the same global PDUs as CanNm.

  5. EcuM: the wakeup source. A wakeup source for the bus, so that a wakeup on body CAN reaches ComM. Recipe 3 completes it with wakeup validation.

  6. BswM: the glue. BswM rules, not parameters of these modules, decide when ComM may communicate on the channel and which I-PDU group entries run: typically a BswMComMIndication for BodyCan as mode request source, and the actions BswMComMAllowCom (with BswMComMAllowChannelRef → BodyCan) and BswMPduGroupSwitch. See lesson 9 and lesson 27.

Check

  • NmComMChannelRef, CanNmComMNetworkHandleRef and CanSMComMNetworkHandleRef point to the same ComMChannel (ECUC_Nm_00217, ECUC_CanNm_00018, ECUC_CanSM_00161).
  • With ComMNmVariant = FULL, NmPassiveModeEnabled must be false, and it must equal CanNmPassiveModeEnabled (ECUC_Nm_00242).
  • CanNmTimeoutTime > CanNmMsgCycleTime, and the same value in every node of the NM cluster (ECUC_CanNm_00020). CanNmWaitBusSleepTime is the same in every node too (ECUC_CanNm_00021). CanNmRepeatMessageTime = n × CanNmMsgCycleTime (ECUC_CanNm_00022).
  • CanNmPduCbvPosition and CanNmPduNidPosition differ when both are used; with node detection the Control Bit Vector must not be CANNM_PDU_OFF (ECUC_CanNm_00026).
  • CanNmNodeId differs from every other node on the bus: here 0x10 against the Door ECU (0x21) and the Light ECU (0x22).
  • NmNumberOfChannels counts every NM channel of the ECU (ECUC_Nm_00201).

Pitfalls

  • A channel that ComM requests but that never reaches full communication: without communication allowed from BswM (ComM_CommunicationAllowed) the channel waits in COMM_NO_COM_REQUEST_PENDING.
  • No CanNmTxPdu: the node can never send NM PDUs, so it is a passive node and cannot keep the bus awake. With the NM variant FULL it needs one.
  • CanIf and CanNm must reference the same global PDU for the NM PDU; two PDUs with the same CAN identifier do not replace that.
  • The node identifier is visible to every ECU on the bus. Change it only together with the network design.

Up to R23-11 a CanIf receive or transmit L-PDU names its upper layer itself: CanIfRxPduUserRxIndicationUL and CanIfTxPduUserTxConfirmationUL = CAN_NM for the NM PDUs (4.4.0, R20-11). R24-11 deleted both parameters; in R25-11 CanIf passes every PDU to the LSduR, which forwards the NM PDUs to CanNm. The LSduR configuration is not part of this course.

Explained in lessons 5, 8, 14, 15, 19, 21, 55, 56.

2. Add a PNC

ComM · NmIf · CanNm · UdpNm · CanSM · CanIf · CanTrcv

Goal. A PNC that a ComM user can request, that wakes only the ECUs of that PNC, and that the gateway forwards between its buses. The example adds Comfort (16, on BodyCan and Eth) and Lighting (17, on BodyCan).

Steps

  1. ComM: switch partial networking on and describe the PNCs. The PNC ID decides the bit in the PNC bit vector; the channel and user lists decide where the PNC runs and who requests it. On the gateway the two PN channels are active PNC gateway channels.

  2. NmIf, global: where the PNC bit vector sits and who computes EIRA and ERA.

  3. NmIf, per NM channel: length, ERA and PNC filter mask. One mask byte per byte of the PNC bit vector; a 1 bit makes the PNC relevant for this ECU.

  4. CanNm and UdpNm: partial networking in the bus NM.

  5. Only for an ECU with a selective wakeup transceiver (the Light ECU of lesson 43, not the gateway): the wakeup frame pattern in CanTrcv and the PN switches in CanIf and CanSM.

Check

  • Byte and bit of a PNC: byteIndex = (ComMPncId div 8) − NmPncBitVectorOffset, bitIndex = ComMPncId mod 8 (SWS_ComM_00825). Comfort: (16 div 8) − 2 = 0, bit 0; Lighting: byte 0, bit 1. The byte index must be smaller than NmPncBitVectorLength.
  • ComMPncId lies in 8 … 511 (ECUC_ComM_00874).
  • NmPncBitVectorOffset equals the number of system bytes of the bus NM, or offset + length equals the NM PDU length (ECUC_Nm_00252). Here: 2 system bytes (node identifier, Control Bit Vector), offset 2.
  • NmPnEraCalcEnabled = true requires NmPnEiraCalcEnabled = true (ECUC_Nm_00251).
  • NmPnResetTime > CanNmMsgCycleTime and > UdpNmMsgCycleTime (ECUC_Nm_00250).
  • NmPnResetTime + ComMPncPrepareSleepTimer < CanNmTimeoutTime, and < UdpNmTimeoutTime (ECUC_ComM_00841). Example: 1 + 0.5 < 2 (BodyCan) and < 3 (Eth).
  • NmPartialNetworkSupportEnabled can only be true while NmCoordinatorSupportEnabled is false (ECUC_Nm_00253); see recipe 5.
  • CanNmPnEnabled is only valid with CanNmGlobalPnSupport = true (ECUC_CanNm_00066). ComMPncNmRequest can only be true with ComMNmVariant = FULL (ECUC_ComM_00886).
  • ComMPncGatewayType is not set on a managed channel (ECUC_ComM_00842).

Pitfalls

  • A PNC bit that is 0 in the filter mask is ignored on that channel, even when other ECUs request it. After adding a PNC, update the mask of every channel it runs on.
  • With partial networking on, CanNm sends the Partial Network Information Bit as 1 (SWS_CanNm_00413) and ignores a received NM PDU with that bit 0 unless CanNmAllNmMessagesKeepAwake is true (SWS_CanNm_00410, SWS_CanNm_00411). The CanNm specification notes that a gateway needs CanNmAllNmMessagesKeepAwake to stay awake on any NM PDU.
  • ComMPncSupport alone is not enough: each channel needs ComMPncEnabled as well.
  • Changing NmPncBitVectorOffset moves every PNC to another byte. All ECUs of the bus must agree on the offset and the PNC IDs.

Up to R24-11 ComMPncEnabled is one switch for the whole ComM configuration, in ComMConfigSet (ECUC_ComM_00878); R25-11 sets it per ComMChannel (ECUC_ComM_00901). In 4.4.0 and R20-11 ComMPncId ranges from 8 to 63, and CanNm and UdpNm compute EIRA and ERA and hand them to ComM through COM signals; recipe 6 moves such a configuration forward.

Explained in lessons 40, 41, 42, 43, 44, 57.

3. Wake up on CAN, with wakeup validation

EcuM · CanTrcv · CanIf · CanSM · ComM

Goal. The body CAN transceiver wakes the sleeping gateway, but ComM starts the channel only after a CAN message has confirmed that the wakeup event was real. The example source is ECUM_WKSOURCE_BODYCAN.

Steps

  1. EcuM: the wakeup source with a validation timeout. Configuring EcuMValidationTimeout at all is what switches validation on for the source.

  2. CanTrcv and CanIf: who detects the wakeup, and validation in CanIf. The transceiver reports the wakeup to the EcuM source it references; CanIf checks it on EcuM_CheckWakeup and remembers received messages for CanIf_CheckValidation.

  3. CanSM and ComM. CanSM starts transceiver and controller for the validation only (state CANSM_BSM_WUVALIDATION); it needs the transceiver of the network for that. ComM decides which channels a wakeup starts.

  4. Integration code, not parameters. The EcuM callouts connect the modules: EcuM_StartWakeupSources calls CanSM_StartWakeupSource(BodyCan), EcuM_CheckValidation calls CanIf_CheckValidation, and EcuM_StopWakeupSources calls CanSM_StopWakeupSource. A BswM rule on BswMEcuMWakeupSource can react to the validated source.

Check

  • A source without EcuMValidationTimeout is not validated at all (ECUC_EcuM_00148).
  • On validation, EcuM_ValidateWakeupEvent calls ComM_EcuM_WakeUpIndication for the channels in EcuMComMChannelRef (SWS_EcuM_02645) and ComM_EcuM_PNCWakeUpIndication for every PNC in EcuMComMPNCRef (SWS_EcuM_04140).
  • EcuMWakeupSourceId lies in 5 … 31; the first five bits are reserved for the predefined sources such as ECUM_WKSOURCE_POWER (ECUC_EcuM_00151).
  • CanTrcvWakeupSourceRef is needed when CanTrcvWakeupByBusUsed is true (ECUC_CanTrcv_00177).
  • CanIfPublicWakeupCheckValidByNM is only configurable with CanIfPublicWakeupCheckValidSupport = true (ECUC_CanIf_00741).
  • For the validation CanSM sets the configured transceiver to normal mode (SWS_CanSM_00623, ECUC_CanSM_00137); a network without CanSMTransceiverId skips that step.

Pitfalls

  • A validation timeout shorter than the time until the first CAN message arrives: the wakeup expires and the ECU goes back to sleep. Leave room for at least one NM PDU cycle (with a Message Cycle Time of 0.5 s, 1 s is a reasonable start; this is a design choice, not a rule of the specification).
  • CanIfPublicWakeupCheckValidByNM = true on a bus where the waking ECU sends application PDUs before its NM PDUs: validation then waits for the first NM PDU.
  • ComMSynchronousWakeUp is true by default: a wakeup on body CAN then wakes ChassisCan and Eth as well.
  • The sleep mode the ECU sleeps in must enable the source in its EcuMWakeupSourceMask; otherwise the transceiver may detect the wakeup but EcuM does not act on it.

Explained in lessons 33, 34, 35, 56.

4. Keep a channel awake for diagnostics

Dcm · ComM

Goal. While a tester works with the gateway on BodyCan, the channel stays in full communication, even when no ComM user needs it. Dcm does this with ComM_DCM_ActiveDiagnostic and ComM_DCM_InactiveDiagnostic; it is not a ComM user.

Steps

  1. Dcm: name the channel of each tester connection. Dcm reports active diagnostics for the channel that DcmDslProtocolComMChannelRef names in the DcmDslMainConnection on which the request arrived.

  2. ComM: nothing to add. No ComMUser for Dcm. What ComM does with the indication depends on the NM variant of the channel:

    ComMNmVariantWhile diagnostics is activeRule
    FULLTreated as a request for full communication; ComM also calls Nm_NetworkRequest, so the whole bus stays awake. The channel leaves COMM_FULL_COM_NETWORK_REQUESTED only when no user and no diagnostics need it.SWS_ComM_00866, SWS_ComM_00870, SWS_ComM_00888
    LIGHT, NONETreated as a request; the channel stays in COMM_FULL_COM_NETWORK_REQUESTED, and after the end at least until ComMTMinFullComModeDuration has run out.SWS_ComM_00866, SWS_ComM_00889
    PASSIVE, SLAVE_ACTIVE, SLAVE_PASSIVEThe requirements on the indication name only FULL, LIGHT and NONE: on these channels it is not treated as a request.SWS_ComM_00866

Check

  • Dcm enters the active diagnostic state on a network when a request arrives there or the session changes to a non-default session (SWS_Dcm_01373), and then calls ComM_DCM_ActiveDiagnostic with the channel of DcmDslProtocolComMChannelRef (SWS_Dcm_01376).
  • It reports inactive when the request is finished, no other protocol is busy on that network and Dcm is in the default session (SWS_Dcm_01374, SWS_Dcm_01377); an S3Server timeout makes all networks inactive (SWS_Dcm_01375).
  • On a FULL, LIGHT or NONE channel, active diagnostics takes COMM_SILENT_COMMUNICATION back to COMM_FULL_COMMUNICATION (SWS_ComM_00878) and COMM_FULL_COM_READY_SLEEP back to COMM_FULL_COM_NETWORK_REQUESTED (SWS_ComM_00883).

Pitfalls

  • A ComM user for Dcm: it would keep the channel through the user interface, outside the session logic of Dcm, and it is not how AUTOSAR connects the two.
  • Several channels for diagnostics: each tester connection has one DcmDslProtocolComMChannelRef, and Dcm reports each channel separately.
  • Dcm ignores Dcm_ComM_NoComModeEntered, Dcm_ComM_SilentComModeEntered and Dcm_ComM_FullComModeEntered for a channel that none of its connections references (SWS_Dcm_01324 to SWS_Dcm_01326).
  • A PASSIVE channel cannot be kept awake by diagnostics; choose the NM variant with the diagnostic use in mind.
  • Active diagnostics has priority over a limitation to no communication (communication inhibition, SWS_ComM_00890), so a limited ECU still answers the tester.

The interface between Dcm and ComM is the same from 4.2.2 to R25-11.

Explained in lessons 8, 10, 11.

5. Coordinate two buses on a gateway

NmIf · CanNm

Goal. The NM coordinator in NmIf keeps BodyCan and ChassisCan awake together and shuts them down so that both reach Bus-Sleep Mode at the same time.

Decide first: NM coordinator or partial networking in NmIf. R25-11 NmIf supports basic functionality plus either the NM coordinator or partial networking, not both (NmIf specification, chapter 7; NmPartialNetworkSupportEnabled can only be true while NmCoordinatorSupportEnabled is false, ECUC_Nm_00253). The example gateway uses partial networking (recipe 2) and therefore has no NM coordinator; lessons 37 to 39 show it in a configuration without partial networking in NmIf. A configuration following this recipe therefore does without NmIf partial networking, or the combination has to be clarified with the supplier of the NmIf.

Steps

  1. NmIf, global: the coordinator. The global coordinator time is the longest TSHUTDOWN_CHANNEL of the cluster; for CanNm that is NM-Timeout Time + Wait Bus-Sleep Time.

    ChannelTSHUTDOWN_CHANNELShutdown timer = 3.5 s − TSHUTDOWN_CHANNEL
    BodyCan2 + 1.5 = 3.5 s0 s: released at once
    ChassisCan1.5 + 1 = 2.5 s1 s

  2. NmIf, per channel: one NM coordination cluster. Both channels get the same cluster index and are coordinated actively.

  3. CanNm: what the coordinator needs from the bus NM.

Check

  • NmGlobalCoordinatorTime is at least the time needed to shut down all coordinated networks (SWS_Nm_00281); each coordinated channel gets NmGlobalCoordinatorTime − TSHUTDOWN_CHANNEL (SWS_Nm_00175); 0 makes every timer 0 (SWS_Nm_00284).
  • A channel with NmCoordClusterIndex must have NmPassiveModeEnabled = false (ECUC_Nm_00221). NmActiveCoordinator is mandatory in a cluster, and at most one channel per cluster may be false (ECUC_Nm_00236).
  • NmCoordinatorSupportEnabled = true requires NmBusSynchronizationEnabled = true (ECUC_Nm_00208) and NmRemoteSleepIndEnabled = true (ECUC_Nm_00207); in a non-passive CanNm, CanNmBusSynchronizationEnabled and CanNmRemoteSleepIndEnabled take the same values (ECUC_CanNm_00006, ECUC_CanNm_00055).
  • At most one synchronizing network per cluster, and only if all its channels are actively coordinated (ECUC_Nm_00223). With none, the shutdown timers start as soon as all shutdown conditions are met (SWS_Nm_00174).
  • A channel with NmChannelSleepMaster = true counts as ready to sleep at all times (SWS_Nm_00228).

Pitfalls

  • NmChannelSleepMaster = true on a CAN bus with other NM nodes: the coordinator would treat the bus as always ready to sleep and ignore the Brake ECU. It is meant for buses whose sleep only this ECU decides, such as a LIN bus where it is the master.
  • Changing a CanNm timer without recomputing NmGlobalCoordinatorTime: the buses then no longer fall asleep together.
  • NmCoordinatorSyncSupport is only needed when another coordinator sits on one of the buses (nested sub-buses, lesson 39).

In 4.4.0 and R20-11 an NmIf supports either basic functionality alone or basic functionality plus the NM coordinator; partial networking is then computed in CanNm and UdpNm, so a gateway can coordinate its buses and use PNCs. From R21-11 on NmIf offers the coordinator or partial networking.

Explained in lessons 37, 38, 39, and in the timer sheet.

6. Move PNC handling from COM signals to NmIf

ComM · NmIf · CanNm · UdpNm · COM · PduR

Goal. A 4.4.0 or R20-11 configuration in which CanNm and UdpNm compute EIRA and ERA and ComM reads them through ComMPncComSignal entries becomes an R25-11 configuration in which NmIf computes them and calls ComM_Nm_UpdateEIRA and ComM_Nm_UpdateERA. The numbers stay; their containers change; the transport through COM and PduR disappears.

Steps

  1. Recognize the old path. ComMPncComSignal containers in ComMPnc, and CanNmPnEiraCalcEnabled set in CanNmGlobalConfig.

  2. Before you start, check the coordinator. If the old ECU also has NmCoordinatorSupportEnabled = true, R25-11 NmIf cannot take over partial networking on the same ECU (recipe 5).

  3. Carry the numbers over. Read the table from left to right:

    4.4.0 and R20-11R25-11Note
    CanNmPnEiraCalcEnabled (CanNmGlobalConfig, ECUC_CanNm_00070), UdpNmPnEiraCalcEnabledNmPnEiraCalcEnabled (NmGlobalProperties)one switch for all buses
    CanNmPnEraCalcEnabled (CanNmChannelConfig, ECUC_CanNm_00067), UdpNmPnEraCalcEnabledNmPnEraCalcEnabled (NmChannelConfig)still per channel
    CanNmPnResetTime (CanNmGlobalConfig, ECUC_CanNm_00059), UdpNmPnResetTimeNmPnResetTime (NmGlobalProperties)one value; it must exceed the Message Cycle Time of every PN bus
    CanNmPnInfoOffset (CanNmPnInfo, ECUC_CanNm_00060)NmPncBitVectorOffset (NmGlobalProperties)4.4.0: 1 … 7, R20-11: 1 … 63, R25-11: 0 … 63
    CanNmPnInfoLength (CanNmPnInfo, ECUC_CanNm_00061)NmPncBitVectorLength (NmChannelConfig)now per channel
    CanNmPnFilterMaskByteIndex, CanNmPnFilterMaskByteValue (CanNmPnFilterMaskByte in CanNmPnInfo, ECUC_CanNm_00063, ECUC_CanNm_00064)NmPnFilterMaskByteIndex, NmPnFilterMaskByteValue (NmPnFilterMaskByte in NmChannelConfig)now per channel
    CanNmPnEnabled, UdpNmPnEnabledthe same, plus NmPnEnabled (NmChannelConfig)both levels exist
    ComMPncEnabled (ComMConfigSet, ECUC_ComM_00878)ComMPncEnabled (ComMChannel, ECUC_ComM_00901)per channel in R25-11
    ComMPncId 8 … 63ComMPncId 8 … 511same byte and bit rule

  4. Delete the transport. Remove every ComMPncComSignal (with ComMPncComSignalDirection, ComMPncComSignalKind, ComMPncComSignalRef, ComMPncComSignalChannelRef), CanNmPnEiraRxNSduRef and CanNmPnEraRxNSduRef (and their UdpNm twins), the PduR routing paths of the EIRA and ERA PDUs, and their COM I-PDUs and signals. ComM now passes its own requests with Nm_UpdateIRA instead of a COM signal in the NM user data.

  5. Keep what is not PNC transport. CanNmComUserDataSupport and CanNmUserDataTxPdu stay if COM still writes other user data into the NM PDU; ComM no longer writes the PNC bits there.

Check

  • The old global CanNm filter mask now has to be repeated for each PN channel; with Ethernet in the example: 0x03 on BodyCan, 0x01 on Eth.
  • The offset rule of R25-11 applies: NmPncBitVectorOffset equals the number of system bytes, or offset + length equals the NM PDU length (ECUC_Nm_00252).
  • No ComMPncComSignal remains: R25-11 ComM does not have the container.

Pitfalls

  • Different old reset times per bus (CanNmPnResetTime and UdpNmPnResetTime) have to become one NmPnResetTime; recheck the rule with ComMPncPrepareSleepTimer (recipe 2) against the shortest NM-Timeout Time.
  • An offset of 0 was not allowed for CanNmPnInfoOffset; it is allowed for NmPncBitVectorOffset only where the bus NM has no system bytes in front of the PNC bit vector.
  • The PNC numbers must not change during the migration: other ECUs on the bus may still run the old release.

The NmIf path came as a draft in R21-11, which declared the COM signal path obsolete; R22-11 removed the COM signal path. From R22-11 on the PNC reset time is NmPnResetTime in NmIf.

Explained in lessons 42, 53, 54, and in the release differences.

7. Add an Ethernet channel with UdpNm and EthSM

ComM · NmIf · UdpNm · EthSM

Goal. The Ethernet link to the Head unit as a ComM channel with network management by UdpNm, started and stopped by EthSM. The example channel is Eth (2), with PNC Comfort on it.

Steps

  1. ComM and NmIf. As in recipe 1, with the Ethernet bus type and UdpNm as bus NM; partial networking as in recipe 2.

  2. UdpNm: the channel. UdpNm has its main function period per channel, and its Remote Sleep Indication time is mandatory.

  3. EthSM: the network.

Check

  • UdpNmTimeoutTime > UdpNmMsgCycleTime, the same in all nodes of the cluster (ECUC_UdpNm_00020).
  • With an offset of 2 the UdpNm NM PDU needs two system bytes in front of the PNC bit vector: node identifier and Control Bit Vector at bytes 0 and 1 (ECUC_Nm_00252).
  • UdpNmComMNetworkHandleRef, NmComMChannelRef and EthSMComMNetworkHandleRef point to the same ComMChannel.

Pitfalls

  • Ethernet hardware that can request a wakeup or sleep on the network is handled with ComMWakeupSleepRequestEnabled on the ComM channel and EthSMWakeupSleepOnDatalineEnabled on the EthSM network; leave them off for a plain link (lesson 23).
  • UdpNm has no bus load reduction; there is no counterpart of CanNmMsgReducedTime.

Explained in lessons 20, 23, 24, 56.

8. Set the NM timers so that the bus sleeps when you want

CanNm · UdpNm · ComM

Goal. Body CAN reaches Bus-Sleep Mode 3.5 s after the last NM PDU on the bus, with NM PDUs every 0.5 s while it is awake.

Steps

  1. Choose the sleep time, then split it. With the network released everywhere, a node enters Bus-Sleep Mode when no NM PDU has been on the bus for NM-Timeout Time + Wait Bus-Sleep Time (PRS_Nm_00506): 2 + 1.5 = 3.5 s. The calculator on the timer sheet also shows the time after a wakeup by another node.

  2. LIGHT channels have no NM timers. There ComM itself decides: ComMNmLightTimeout after the last request, and at least ComMTMinFullComModeDuration in full communication.

Check

  • CanNmTimeoutTime > CanNmMsgCycleTime (ECUC_CanNm_00020); CanNmRepeatMessageTime = n × CanNmMsgCycleTime and > CanNmImmediateNmTransmissions × CanNmImmediateNmCycleTime (ECUC_CanNm_00022): 1.5 = 3 × 0.5, and 1.5 > 3 × 0.02.
  • NM-Timeout Time and Wait Bus-Sleep Time are the same in every node of the cluster.
  • With partial networking: NmPnResetTime + ComMPncPrepareSleepTimer < CanNmTimeoutTime (ECUC_ComM_00841).
  • With an NM coordinator: NmGlobalCoordinatorTime covers the new shutdown time (recipe 5).

Pitfalls

  • CanNmStayInPbsEnabled = true: the node stays in Prepare Bus-Sleep Mode until a restart or power-off, and the Wait Bus-Sleep Time is not used.
  • A bus that never sleeps is rarely a timer problem: some node, user or active diagnostics still keeps the network requested. See the troubleshooting guide.

Explained in lessons 8, 13, 14, and in the timer sheet.
