SOME/IP in AUTOSAR Classic

SOME/IP

OfferService and the TTL

A server makes each service instance known with an OfferService: a statement of where the instance can be reached and for how long the statement stays valid. Clients trust it only until that time runs out, so the server keeps renewing it.

Entries and options

Sd has its own messages. A SOME/IP-SD message (a SOME/IP message of the Service Discovery service, Service ID 0xFFFF) travels over UDP (the connectionless transport, lesson 22) to a fixed port, 30490 by default. It goes either by multicast (once to a group address that every listening ECU receives) or by unicast (to one ECU at its own IP address). One SD message carries a list of entries (single statements, such as "this service instance is offered") and a list of options (additional information an entry points to). Each entry names the options it needs.

The entry a server uses is the OfferService (the statement "this service instance is available, for TTL seconds"). Where to reach the instance is in its Endpoint options (an IP address, a port and UDP or TCP).

The Endpoint options of an offer are not just for method calls. The server also sends its events from exactly these addresses and ports, so a client knows where the events of this service instance come from.

The TTL

Every OfferService carries a TTL (time to live: how many seconds the offer stays valid unless renewed). A client counts the service instance as available only while the TTL runs. The server sends a new offer before the old TTL ends, and each one starts the TTL again. If the offers stop, for whatever reason, the TTL runs out and clients drop the service instance on their own. This makes an offer soft state (state that disappears by itself unless renewed in time); the TTL works like a lease.

normal end

StopOfferService

A server that shuts a service instance down sends a StopOfferService (the OfferService entry with TTL 0). Clients drop the service instance at once.

special TTL

"Until reboot"

The highest TTL value means "valid until the next reboot". Then nothing expires on its own, and the server need not repeat its offers; reboot detection (noticing that a partner restarted, lesson 16) takes over.

why a TTL

No goodbye needed

A crashed ECU or a broken cable cannot send a StopOfferService. With a TTL, the rest of the network still notices.

Try it

The radar sends an OfferService every 2 seconds. Pick a TTL, start the clock, then break things: lose one offer, crash the server, or stop properly.

Things to notice. A TTL shorter than the repeat makes the service instance flicker between available and gone. One lost OfferService does no harm when the TTL is longer than the repeat. After a crash the client needs up to one TTL to notice. With "until reboot" a crash is never noticed this way; the StopOfferService still works.
