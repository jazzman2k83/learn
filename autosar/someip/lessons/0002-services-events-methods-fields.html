SOME/IP in AUTOSAR Classic

SOME/IP

Services: events, methods and fields

A service is a set of three kinds of things: events the server sends, methods the server answers, and fields whose values the server keeps.

Three kinds of parts

A service (a set of events, methods and fields that belong together) is described by a service interface (the description of its events, methods and fields with their data types and its version). The running example of this course is a radar service. A radar ECU is its server; a brake ECU is a client. The example follows the one in the AUTOSAR System Template.

server → clients

Events

An event (a message the server sends on its own, without being asked) says that something happened or a value changed. Example: BrakeEvent, "obstacle ahead, brake".

client → server, maybe back

Methods

A method (a function of the server that a client calls) comes in two kinds. Request/response (the client sends a request and gets a response): Calibrate, Adjust. Fire&forget (the client sends a request and nothing comes back): Reset, LogCurrentState.

kept by the server

Fields

A field (a value the server owns) always has a value. It has up to three parts: a getter (clients read the value), a setter (clients change it) and a notifier (an event sent when the value changes). Example: UpdateRate.

IDs, not names

On the wire nobody sends names. The service has a Service ID (a 16-bit number, here 0x1234), and every method has a Method ID and every event an Event ID (16-bit numbers within the service). Method IDs come from the lower half of the range and Event IDs from the upper half, so a receiver sees at once which kind it is.

The service interface also has a version. The major version (the part that must match exactly between server and client) changes when old clients will not understand the server any more. The minor version (the compatible part) changes for compatible extensions.

Events come in eventgroups

A client does not subscribe to single events. It subscribes to an eventgroup (a set of events and fields of one service that the server publishes together), identified by an Eventgroup ID (a 16-bit number within the service). Every event belongs to at least one eventgroup, and an eventgroup is never empty. The notifier of a field is an event, so it also lives in an eventgroup.

Service instances

A car can have the same service more than once: a front radar and a rear radar both offer the radar service. Each is a service instance (one running copy of the service) with its own Instance ID (a 16-bit number that tells apart instances of the same service). Clients pick the instance they want when they look for it.

The Instance ID appears when servers and clients find each other in Service Discovery (part 3). It is not repeated in every message: once found, the server's IP address and port tell the instances apart.

How the Classic Platform writes it down

The Classic Platform has no single "service" element. A service is put together from ordinary port interfaces and grouped in a collection:

Part of the serviceWritten down as
EventA data element of a sender-receiver interface
Method, request/responseAn operation of a client-server interface
Method, fire&forget, with dataA data element of a sender-receiver interface (the client sends, the server receives)
Method, fire&forget, without dataA trigger of a trigger interface
Field: notifier, getter, setterA data element for the notifier, plus a client-server operation each for getter and setter

So an SWC (software component: the application software above the RTE) that uses SOME/IP still calls the usual RTE functions: write and read for events, call for methods. It does not see SOME/IP at all.
