SOME/IP

Server and client

For each service instance, one ECU is the server and others are clients. Each role comes with its own duties, from power-up to shutdown.

Two roles, one service instance

Roles belong to a service instance, not to an ECU. The brake ECU of this example is the client of the radar and, at the same time, the server of its own brake service.

The duties

Both roles talk through Sd, the subject of the next part. A few SD entries carry most of it: OfferService (from the server: "this service instance is available here", valid for a TTL, a time to live, and repeated), FindService (from the client: "who offers this service?"), SubscribeEventgroup (from the client: "send me the events of this eventgroup"), answered by SubscribeEventgroupAck (accepted) or SubscribeEventgroupNack (refused), and StopOfferService (the service instance is no longer available).

server

Offer and serve

Send OfferService while the service instance is available, answer FindService, accept or refuse each SubscribeEventgroup, send events only to subscribers (and the initial event of each field to each new subscriber), answer each REQUEST, and send StopOfferService when going away.

client

Find and use

Send FindService when the service is needed and not yet known, subscribe to the wanted eventgroups and renew the subscriptions, open the TCP connection if the service uses TCP, call methods and handle timeouts, and drop everything when the server sends StopOfferService.

Note the one duty that is easy to miss: if a service instance uses TCP, it is always the client that opens the connection, before subscribing, and the client that closes it.

How AUTOSAR names the two sides

The Sd module of an ECU keeps one configuration container per service instance and role. An SdServerService (one service instance this ECU offers as server) lists its event handlers (the server side of an eventgroup, which keeps the subscribers) and the methods it provides. An SdClientService (one service instance this ECU uses as client) lists its consumed eventgroups (the client side of an eventgroup, which subscribes) and the methods it calls.

Things to notice. The server never needs to know in advance who its clients are; it learns them from each SubscribeEventgroup. The client never needs to know the server's address in advance; it learns it from the OfferService.
