SOME/IP

Socket connections and routing groups

Inside SoAd every network partner gets a socket connection, and every route through it can be switched on and off by a routing group. Sd fills in the partners' addresses and switches the routing groups; that is how a SubscribeEventgroup turns into actual event flow.

Socket connections

A socket connection connects one local port of the ECU with one partner: its IP address and port, over UDP or TCP. Socket connections with the same local port and settings form a socket connection group (socket connections that share one local port and protocol), one socket connection per partner. A socket connection can start with a wildcard remote address (any address: the partner is not known yet) and get the real address later.

filled by Sd

From Endpoint options

When an OfferService or a SubscribeEventgroup brings an Endpoint option, Sd writes that address into a free socket connection of the right group that still has the wildcard remote address, or finds the socket connection that already has it.

filled on arrival

From the first message

A UDP socket connection with the wildcard remote address can also take the address of the first accepted message that arrives through it. This is how a server's socket connection learns which client is calling.

opened by Sd

Open and close

Sd asks SoAd to open the socket connections of a service instance when it starts using it, and to close them when it stops. A TCP socket connection on the client side opens the TCP connection.

Routing groups

A routing group works like a named switch attached to routes: a PDU route (the way of a PDU from PduR out to its socket connections) or a socket route, which takes a received message from a socket connection up to a module by its header ID. When all routing groups of a route are off, nothing flows on it. A routing group attached to a socket connection group has a separate on/off for each socket connection, so it can be on for one partner and off for another.

Which routing groups Sd uses

Responses find their way back

On the server, REQUESTs from several clients arrive through different socket connections of one socket connection group. The RTE keeps the PDU meta data of each REQUEST (extra data that travels with a PDU; here the socket connection ID) and hands it back with the RESPONSE, so SoAd sends the RESPONSE through that same socket connection to the right client.
