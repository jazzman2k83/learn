SOME/IP

Events

An event is a one-way message from the server to every client that subscribed to its eventgroup. Nobody answers it.

How an event travels

On the wire an event travels with the Message Type NOTIFICATION. A receiver never sends a response and never sends an ERROR back for an event, even if it cannot read it. Each client that receives it is a subscriber (a client whose subscription to the eventgroup is currently accepted). Subscribing is the job of Service Discovery (lesson 14); this lesson only looks at the event itself.

When does the server send?

SOME/IP itself does not say when an event is sent. The specification names three common strategies:

at a fixed period

Cyclic update

A cyclic update (sent at a fixed period, changed or not) carries the current value, for example every 100 ms. Good for safety-related values the receiver watches.

on every change

Update on change

An update on change (sent only when the value changes) goes out as soon as the value changes, for example "door opened".

on a large change

Epsilon change

An epsilon change (sent only when the value changes by more than a set amount) skips the small steps since the last send.

The receiver cannot tell which strategy the sender uses; a NOTIFICATION looks the same either way. One server can even mix strategies for one event. In the Classic Platform the sending side decides, through when the SWC writes the value and how the transmission of the PDU is configured below the RTE.

Optional: the Session ID of an event

An event has no client, so the Client ID in the Request ID is 0. With session handling on, the Session ID counts each NOTIFICATION, so a receiver can spot gaps; with session handling off it stays 0 for this event.

Try it

The radar measures a distance that changes now and then. Choose a strategy, choose which clients are subscribed, and press "Start". You can change the subscriptions while the clock runs.

Things to notice. The value lane is the same every run; only the NOTIFICATION lane changes with the strategy. A client that is not subscribed gets nothing, and a client that subscribes in the middle only gets events from then on: a plain event does not repeat the old value for a new subscriber (a field does: its initial event, the current value sent once to a new subscriber, lesson 8).
