SOME/IP

Methods: request and response

A client sends a REQUEST, the server runs the method and sends back a RESPONSE that carries the same Request ID, so the client knows which request it belongs to.

REQUEST and RESPONSE

client

The REQUEST

Message Type REQUEST. The payload holds the input arguments in the order the method lists them. The Session ID takes the next value.

server

The RESPONSE

Built from the SOME/IP header of the request: same Message ID, same Client ID and Session ID. Message Type RESPONSE, the Return Code E_OK, the output arguments as payload.

client

The match

A response whose Request ID does not match an open request is ignored. A response to a request that was not completely sent yet is ignored too.

Waiting has a limit

Over UDP (connectionless transport, lesson 22) a message can get lost and nobody repeats it. SOME/IP calls this reliability "maybe". So the client side waits only for a set time. If no matching response arrives, the call ends with E_TIMEOUT (no response in time; in the RTE the call returns RTE_E_TIMEOUT) instead of a result, and whether to try again is up to the application.

Over TCP (connection-oriented transport that repeats lost data) a request and its response arrive "exactly once". If the TCP connection breaks, every request still waiting is treated as timed out.

Who does what in the Classic Platform

The SWC calls a ClientServerOperation (a function of a client-server interface, with its IN, INOUT and OUT arguments) through the RTE, as for any client-server call. For each call the RTE keeps a transaction handle (client ID and sequence counter, which become the Client ID and Session ID on the wire) and monitors the timeout. On the network side it allows only one open request per client and operation at a time, so a response can always be matched; the sequence counter also lets it recognise a stale response that arrives after a timeout.

The Client ID names the calling client inside its ECU. It can carry a fixed prefix so that it is unique in the whole vehicle.

Things to notice. In "RESPONSE lost" the server did its work, yet the client reports E_TIMEOUT: the client cannot tell a lost request from a lost response. In "Late RESPONSE" the old response still arrives, but its Session ID no longer matches the open request, so it is ignored.
